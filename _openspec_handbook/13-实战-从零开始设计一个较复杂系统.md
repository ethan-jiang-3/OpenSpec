# 13 · 实战：从零开始设计一个较复杂系统

> `11` 讲的是已有系统上的增量 change。
> 这一篇换一个更难、也更容易想错的场景：**从零开始做一个复杂系统时，OpenSpec 到底怎么用。**

---

## 开始前的准备：这个案例假设你已经...

**必须先读过的**：
- `01` 初级篇 + `02` 中级篇 - 基础概念
- `11` brownfield 实战篇 - 理解单个 change 怎么走
- `12` artifact 修改篇 - 理解 artifacts 生成后怎么安全调整

**如果没读过 11**：
- 你会不理解"为什么第一版也要用 change"
- 你会不理解"多域 spec 是什么意思"

**建议**：greenfield 案例比 brownfield 更复杂，先看 11 和 12，再看 13。

---

## 这一篇为什么重要

很多人看 OpenSpec 时，很容易把它理解成：

- 更适合已有项目
- 更适合小步迭代
- 更适合在老系统上做 change

这个理解只对了一半。

OpenSpec 当然很擅长管理增量变化，但这并不表示：

- 新系统就不用它
- 从零开始时就回到"先写一堆 PRD，再让 AI 一把梭"

恰恰相反。

对于一个从零起步、但复杂度较高的新系统，OpenSpec 反而更有价值，因为它能帮你避免最危险的两种失败：

1. 一上来就把未来三年的蓝图写成一坨大文档
2. 一上来就直接写代码，最后做出一套边界混乱的东西

所以这一篇的核心问题不是：

- 从零开始时还要不要用 `changes/`

而是：

- **从零开始时，第一个 change 应该怎么切，才能既有系统整体性，又不失控。**

---

## 先选一个足够复杂、但又现实的系统

我们不用"Todo App"这种太轻的例子。

我们选一个更有企业感、模块更多、角色更复杂的系统：

> **做一个企业内部采购申请与审批平台。**

暂时给它起名：

```text
ProcureFlow
```

这个系统的典型目标是：

- 员工提交采购申请
- 按部门、金额和预算规则走审批流
- 审批通过后进入采购执行
- 关键动作触发通知
- 全流程保留审计记录

你一看就知道，这不是一个小玩具。

它至少天然包含这些能力线：

- 身份与角色
- 采购申请
- 审批流
- 通知
- 审计日志
- 预算约束
- 后台管理

如果没有一个很强的结构化方法，这种系统特别容易在第一周就失控。

---

## 第一个关键认知：从零开始，也不是"一次性定义整个宇宙"

这是 greenfield 场景里最容易犯的错误。

很多团队一说"从零开始"，脑子里立刻冒出这种冲动：

- 那我们就把整个采购平台全定义了
- 多级审批、代理审批、驳回重提、预算冻结、供应商管理、付款对接、ERP 集成、报表中心、移动端、国际化，全都先写进去

这会导致什么？

- proposal 巨大
- specs 巨大
- design 巨大
- tasks 巨大
- AI 和人都看不住边界

最后你得到的不是"清晰"，而是"巨大而模糊"。

OpenSpec 更鼓励一种完全不同的做法：

> **从零开始，不等于一次写完整系统；而是先定义第一版可成立的正式基线。**

也就是说，你不是在做：

- "永恒最终版系统设计"

而是在做：

- "第一个可以成立、可以实现、可以 archive 成正式基线的复杂系统 MVP"

这句话特别重要。

---

## 这次案例怎么切第一版边界

我们先约束第一个 change，只做一个能闭环的采购申请 MVP。

### 本次 change 要覆盖什么

- 员工登录系统
- 员工创建采购申请
- 主管审批或驳回
- 审批结果通知申请人
- 系统记录关键审计事件

### 本次 change 明确不做什么

- 多级审批链
- 预算联动
- 采购执行跟踪
- 供应商管理
- ERP 对接
- 移动端支持

看得出，这已经不小了。

但它依然是一个：

- 可讲清
- 可拆分
- 可实现
- 可 archive

的第一版复杂系统基线。

---

## 第 0 步：项目一开始是什么样

现在假设项目刚初始化，代码和 OpenSpec 都还很空：

```text
procure-flow/
├── src/
├── tests/
└── openspec/
    ├── changes/
    ├── specs/
    └── config.yaml
```

这时候最重要的事实是：

- `openspec/specs/` 还几乎是空的
- 所以当前系统还没有正式能力基线

正因为如此，第一个 archive 的意义会非常大。

因为它会把"没有正式 spec"推进到"有第一版正式 spec"。

---

## 第 0.5 步：从零开始时，先把"全局层"和"change 层"分开

下面这类东西，其实正是复杂系统最容易放错位置的一层：

- 目录结构约束
- TDD 原则
- 编码风格
- regression 要求
- 架构边界
- 测试分层要求

这些东西有一个共同点：

- 它们**不属于某一个 change**
- 它们也**不等于系统当前能力规格**
- 它们影响的是整个项目的长期开发方式

所以在 OpenSpec 里，最好把它们明确放进"项目全局层"，而不是塞进某一个 `proposal.md` 或 `tasks.md`。

更实用的三层分法是：

### 第一层：项目全局工程约束

放在：

```text
openspec/config.yaml
```

这里更适合放：

- 项目背景
- 团队长期原则
- 测试和回归要求
- 目录和模块约束
- 编码风格与工程纪律

### 第二层：项目当前正式能力边界

放在：

```text
openspec/specs/
```

这里放的是：

- 系统现在正式承认自己具备什么能力
- 用户和系统行为的正式合同

### 第三层：某一次 change 的临时工作区

放在：

```text
openspec/changes/<change-id>/
```

这里放的是：

- 这次为什么做
- 这次要改哪些行为
- 这次打算怎么实现
- 这次任务怎么拆

这三层如果混了，后面会很难读，也很难让 AI 稳定工作。

---

## 第 0.6 步：给这个 greenfield 项目先写一个项目级 `config.yaml`

对于 `ProcureFlow` 这样的系统，一个很有代表性的项目级 `openspec/config.yaml` 可以写成：

```yaml
schema: spec-driven

context: |
  Project: ProcureFlow
  Domain: Internal procurement request and approval platform
  Stack: TypeScript, React, Node.js, PostgreSQL
  Architecture intent:
  - Build the MVP as a modular monolith with explicit domain boundaries
  - Core domains include auth, requests, approvals, notifications, and audit
  - Prefer clear service boundaries over framework-driven coupling

rules:
  design:
    - Keep domain code grouped by capability, not by technical layer only
    - Do not introduce cross-domain imports that bypass published module interfaces
    - Prefer additive changes over hidden behavioral rewrites
  specs:
    - New user-visible behavior must be reflected in OpenSpec artifacts before or during implementation
  tasks:
    - Use TDD or test-first increments for core domain logic and approval state transitions
    - Every change must preserve regression coverage for request submission and approval workflows
    - Do not merge a change with incomplete authorization checks
  risk:
    - Keep audit records append-only
  structure:
    - Place request domain code under src/requests/
    - Place approval domain code under src/approvals/
    - Place audit domain code under src/audit/
    - Shared UI components belong in src/ui/, not inside domain folders unless domain-specific
    - Integration tests live under tests/integration/
    - Domain unit tests live next to the domain module or under tests/unit/ with mirrored paths
  regression:
    - Changes touching request creation must keep end-to-end request submission coverage green
    - Changes touching approvals must keep approval decision and authorization regression tests green
    - Changes touching notifications must verify decision events still trigger notification work
    - Changes touching audit logic must verify audit records are still emitted for key lifecycle events
```

这个例子里最重要的不是字段长短，而是边界意识。

### 这些内容为什么适合放 `config.yaml`

因为它们回答的是：

- 这个项目长期怎么开发
- 这个团队长期怎么约束 AI 和人
- 这个代码库长期怎么保持结构稳定

它们不是某个 change 的局部意图，也不是某个具体功能的行为规格。

---

## 第 0.7 步：一定要分清"全局原则"和"能力规格"不是一回事

这里再往前走一步，因为这是最容易混淆的地方。

### 适合放进 `config.yaml` 的

- 代码目录怎么组织
- 是否要求 TDD
- 回归测试最低要求
- 编码风格和模块边界
- 哪些风险必须显式验证

### 不适合只放进 `config.yaml` 的

- "系统支持经理审批"
- "系统会给申请人发送审批通知"
- "系统记录审计事件"

这些不是工程原则，而是**系统能力承诺**，所以必须出现在 `specs/`。

### 更不适合放进某个单一 change 的

- "整个项目都必须遵守模块边界"
- "所有审批相关变更都必须保住 regression"

因为这些会跨越很多 change，属于项目级长期约束。

一句话总结就是：

> **项目怎么开发，看 `config.yaml`；系统现在会什么，看 `specs/`；这次准备改什么，看 `changes/`。**

---

## 第 1 步：不是先画超级大图，而是先开第一个 change

在 OpenSpec 的思路里，从零开始也仍然是：

```text
/opsx:propose bootstrap-procurement-mvp
```

这里 change 名字就很关键。

它不叫：

- `build-procurement-platform`
- `enterprise-procurement-system`

而是叫：

- `bootstrap-procurement-mvp`

这会逼你承认一件很现实的事：

> **你不是在一口气完成整个系统，而是在建立第一版正式基线。**

这一步对 greenfield 特别重要，因为它天然抑制 scope 失控。

---

## 第 2 步：`proposal.md` 先解决"第一版到底算什么"

一个合理的 `proposal.md` 可以写成这样：

```markdown
# Proposal: Bootstrap Procurement MVP

## Intent
Establish the first formal baseline for an internal procurement workflow system.
The MVP should support request submission, manager approval, decision notification,
and auditability for key actions.

## Scope
- Employee authentication and role identification
- Purchase request creation and viewing
- Single-step manager approval or rejection
- Notification to requester after approval decision
- Audit logging for request lifecycle events

## Out of Scope
- Multi-step approval chains
- Budget policy integration
- Procurement execution tracking
- Supplier and catalog management
- ERP integration
- Mobile client support

## Success Criteria
- A requester can submit a purchase request with basic fields
- A manager can approve or reject pending requests
- Requester receives a notification after decision
- Key actions are queryable in audit history
```

这里要特别注意一个不同于 `11` 的点：

在已有系统里，proposal 常常是在一个明确基线上改一块。

但在 greenfield 里，proposal 更像是在回答：

- 第一版系统最小成立条件是什么？

这和"未来梦想清单"完全不是一回事。

---

## 第 3 步：从零开始时，spec 不是一份，而往往是多份

这是复杂系统和 `11` 最大的不同之一。

在 `11` 里，你主要改的是订单域的一份 spec。

但在这个 greenfield 复杂系统里，第一个 change 很可能会同时创建多条基线能力线。

比如：

```text
openspec/changes/bootstrap-procurement-mvp/
├── proposal.md
├── design.md
├── tasks.md
└── specs/
    ├── auth/
    │   └── spec.md
    ├── requests/
    │   └── spec.md
    ├── approvals/
    │   └── spec.md
    ├── notifications/
    │   └── spec.md
    └── audit/
        └── spec.md
```

这件事本身就说明：

- 复杂系统不是靠一份 spec 包打天下
- 而是靠多个 capability 域的正式 spec 共同组成系统基线

---

## 第 4 步：先看 `requests/spec.md`，理解"系统骨架"怎么写成 spec

从零开始时，很多人会先去写 UI 流程。

OpenSpec 更好的顺序，是先写能力域的行为合同。

比如 `requests/spec.md` 可以长这样：

```markdown
# Requests Specification

## Requirements

### Requirement: Create Purchase Request
The system SHALL allow an authenticated employee to create a purchase request.

#### Scenario: Employee submits a request
- GIVEN an authenticated employee
- WHEN the employee submits a request with title, amount, justification, and department
- THEN the system stores the request
- AND assigns it a Pending status

### Requirement: View Owned Requests
The system SHALL allow a requester to view purchase requests they created.

#### Scenario: Requester opens request list
- GIVEN an authenticated employee with submitted requests
- WHEN the employee opens the request list
- THEN the system displays requests created by that employee
```

这一步的意义是：

- 你不是在先写表结构
- 也不是先想页面长啥样
- 而是在先定义"采购申请域的正式行为"

这就是从零开始时，OpenSpec 很强的一点：

> **它逼你先说清系统要成为什么，而不是先堆实现碎片。**

---

## 第 5 步：再看 `approvals/spec.md`，理解复杂系统里的跨角色行为

复杂系统和简单系统的差别之一，是经常会涉及不同角色之间的动作链。

比如 `approvals/spec.md` 可以是：

```markdown
# Approvals Specification

## Requirements

### Requirement: Manager Decision
The system SHALL allow an authorized manager to approve or reject pending purchase requests.

#### Scenario: Manager approves a request
- GIVEN a pending request assigned to a manager
- WHEN the manager approves the request
- THEN the request status becomes Approved

#### Scenario: Manager rejects a request
- GIVEN a pending request assigned to a manager
- WHEN the manager rejects the request with a reason
- THEN the request status becomes Rejected
- AND the rejection reason is stored

### Requirement: Decision Visibility
The system SHALL expose the latest approval decision to the requester.

#### Scenario: Requester views a rejected request
- GIVEN a requester with a rejected request
- WHEN the requester opens request details
- THEN the system shows the rejection status and reason
```

这一步的价值在于：

- 行为是按角色和状态流写清楚的
- 不是一句抽象的"支持审批"

对于复杂系统，spec 如果不把角色、状态、触发条件写清，后面设计和实现都会乱。

---

## 第 6 步：通知和审计为什么也要单独成 spec

很多团队第一次做系统时，会把通知和审计当"实现细节"。

但对复杂业务系统来说，它们常常不是细节，而是正式能力。

### `notifications/spec.md`

```markdown
# Notifications Specification

## Requirements

### Requirement: Decision Notification
The system SHALL notify the requester after a manager approves or rejects a request.

#### Scenario: Notification after approval
- GIVEN a requester with an approved purchase request
- WHEN the approval decision is recorded
- THEN the system sends a notification to the requester
```

### `audit/spec.md`

```markdown
# Audit Specification

## Requirements

### Requirement: Audit Request Lifecycle Events
The system SHALL record auditable events for request creation and approval decisions.

#### Scenario: Audit event on request submission
- GIVEN an employee submits a purchase request
- WHEN the request is successfully created
- THEN the system records an audit event containing actor, action, target, and timestamp
```

把这两块单独拉出来，意义非常大：

- 它提醒所有人：这不是可有可无的"附带功能"
- 它让 AI 不会默认只盯着主业务页面
- 它让"系统完整性"在第一版就被正式表达出来

---

## 第 7 步：greenfield 的 `design.md`，重点不是细枝末节，而是系统骨架决策

一个从零开始的复杂系统，`design.md` 的角色会比 `11` 更重。

因为它通常要回答这些基础问题：

- 先做模块化单体还是微服务
- 状态流怎么表示
- 通知是同步发还是异步事件驱动
- 审计日志怎么落
- 权限模型怎么切

一个合理的 `design.md` 大概会长这样：

```markdown
# Design: Bootstrap Procurement MVP

## Architecture
Use a modular monolith for the MVP with clear domain boundaries:
- auth
- requests
- approvals
- notifications
- audit

## Decisions

### Decision: Modular Monolith First
The MVP should remain in a single deployable application to reduce operational complexity,
while preserving module boundaries for future extraction if needed.

### Decision: Explicit Request State Model
Purchase requests use explicit states: Draft, Pending, Approved, Rejected.

### Decision: Asynchronous Notification Delivery
Approval decisions should enqueue notification work to avoid coupling user-facing decision latency
to notification channel availability.

### Decision: Append-Only Audit Records
Audit entries are append-only and cannot be modified by application users.

## Risks
- Authorization rules may expand quickly once multiple approval layers are introduced
- Notification retries may need a job runner in later phases
- Audit retention requirements may affect storage design
```

你会发现这份 design 和已有系统上的 design 很不一样。

它不是在微调一个局部策略，而是在定义：

- 第一版系统骨架
- 第一版模块边界
- 第一版关键技术立场

这就是 greenfield 复杂系统里 design 的核心角色。

---

## 第 8 步：`tasks.md` 不只是列功能，而是要能承受多人并行

复杂系统一旦进入实施，往往不是一个人顺序做完。

所以 `tasks.md` 如果只是写：

- 做登录
- 做申请
- 做审批

这种粒度会非常差。

一个更合理的 `tasks.md` 可以是：

```markdown
# Tasks

## 1. Foundation
- [ ] 1.1 Set up authentication and role model
- [ ] 1.2 Establish request domain entities and persistence
- [ ] 1.3 Define request state transitions

## 2. Request Workflow
- [ ] 2.1 Implement request creation API
- [ ] 2.2 Implement requester request list and detail view
- [ ] 2.3 Validate required fields and amount format

## 3. Approval Workflow
- [ ] 3.1 Implement manager pending queue
- [ ] 3.2 Implement approve action
- [ ] 3.3 Implement reject action with reason

## 4. Notifications
- [ ] 4.1 Define notification event payload
- [ ] 4.2 Queue notification after decision
- [ ] 4.3 Deliver in-app notification to requester

## 5. Auditability
- [ ] 5.1 Record request creation audit event
- [ ] 5.2 Record approval decision audit event
- [ ] 5.3 Add audit history query for administrators

## 6. Verification
- [ ] 6.1 Test requester workflow end to end
- [ ] 6.2 Test manager decision workflow
- [ ] 6.3 Test unauthorized approval attempts are rejected
- [ ] 6.4 Test audit records are created for key actions
```

这个任务结构的好处是：

- 可以并行
- 可以追踪
- 可以对应回各个 spec 域
- 可以让 AI 或不同工程师各自拿一段推进

---

## 第 9 步：从零开始时，最危险的不是"文档不够"，而是"scope 假装稳定"

greenfield 项目经常有一个幻觉：

- 反正还没实现，那就先多写一点也没事

其实恰恰相反。

因为从零开始时，未知数最多，所以最需要警惕的不是文档少，而是：

- scope 看起来很大很全
- 但里面大量东西其实还没想清楚

### 一个典型危险信号

你本来只想做 MVP，却在第一版 change 里开始加入：

- 多级审批链
- 金额阈值自动路由
- 邮件 + 短信 + 站内信多通道通知
- 预算中心联动
- 供应商比价

这时最应该做的，不是"再努力把 design 写完整"。

而是停下来问：

- 这些是不是应该拆成后续 change？

OpenSpec 的答案通常是：**是。**

---

## 第 10 步：复杂系统从零开始时，怎么判断"该拆新 change 了"

这里给你一个很实用的判断法。

如果新增内容同时满足下面任意两条，就强烈说明它应该另开 change：

1. 它引入了新的核心角色关系
2. 它引入了新的状态机或流程分支
3. 它引入了新的外部系统依赖
4. 它让已有 MVP 的成功标准发生明显变化
5. 它会让 review 者必须重新理解整个 proposal

### 套到这个案例里

比如"加预算联动"就很明显该新开 change，因为它：

- 引入新的业务规则源
- 引入新的失败模式
- 可能引入新的系统依赖
- 会改变审批能否通过的核心语义

所以这不该偷偷塞进 `bootstrap-procurement-mvp`。

更合理的是后续再开：

```text
/opsx:propose add-budget-policy-gates
```

这就是 OpenSpec 在 greenfield 场景里的一个关键作用：

> **不是阻止系统生长，而是阻止第一版 change 失控。**

---

## 第 11 步：`/opsx:apply` 期间，复杂系统往往会逼你修正系统骨架

现在开始实施：

```text
/opsx:apply bootstrap-procurement-mvp
```

做到一半时，很可能会出现这种情况：

- 审批决定写入后，要立即通知申请人
- 但通知服务偶发失败
- 如果同步发送通知，审批动作就会被拖慢甚至失败

这时你会发现，原来"通知只是个附带动作"的想法太天真了。

于是你回头修正 `design.md`：

- 明确通知走异步队列
- 审批动作和通知投递解耦

如果相应行为表达要更精确，也可以顺手补 `notifications/spec.md`。

比如把原来宽泛的"系统发送通知"澄清成：

- 审批决定成功记录后，系统必须触发一条通知任务

这一步再次说明：

- `apply` 不是末端流水线
- 它会反过来修正设计和规格

在复杂系统里，这种反馈尤其常见。

## 第 12 步：archive 的意义，在 greenfield 里比 brownfield 还大

在已有系统里，archive 的作用是把增量变化沉淀回正式基线。

在从零开始的系统里，archive 的意义更进一步：

> **它把"还没有正式系统定义"的状态，推进成"系统已经拥有第一版正式基线"的状态。**

也就是说，执行：

```text
/opsx:archive bootstrap-procurement-mvp
```

以后，`openspec/specs/` 不再是空架子，而会长成类似这样：

```text
openspec/
├── specs/
│   ├── auth/spec.md
│   ├── requests/spec.md
│   ├── approvals/spec.md
│   ├── notifications/spec.md
│   └── audit/spec.md
└── changes/
    └── archive/
        └── 2026-04-20-bootstrap-procurement-mvp/
            ├── proposal.md
            ├── design.md
            ├── tasks.md
            └── specs/
                ├── auth/spec.md
                ├── requests/spec.md
                ├── approvals/spec.md
                ├── notifications/spec.md
                └── audit/spec.md
```

这时项目第一次真正拥有了：

- 当前系统正式能力边界
- 各域的正式 spec 文件
- 第一版系统骨架的技术理由
- 第一版实现过程的完整历史

这就是 archive 在 greenfield 中的"立国"意义。

---

## 第 13 步：archive 以后，后续 change 会怎么长出来

一旦第一版基线建立，后面的 change 就不再是"从零发明系统"，而是：

- 在已有基线上继续演化

比如后续可能自然长出这些 change：

```text
/opsx:propose add-budget-policy-gates
/opsx:propose support-multi-step-approval
/opsx:propose add-supplier-catalog
/opsx:propose integrate-erp-purchase-order-export
```

注意这个转换非常重要。

在 archive 之前，你在定义：

- 第一版系统是什么

在 archive 之后，你在管理：

- 第一版系统如何演化

这也说明了 OpenSpec 其实非常适合 greenfield：

- 它不是只会维护老系统
- 它能把"从无到有"平滑地转成"从有到优"

## 第 14 步：这个案例里，最值得学的不是目录，而是切法

如果这篇只让你记住目录结构，那价值还不够。

真正该带走的是这种切法：

### 1. 先切"第一版成立条件"，不是切"最终愿景"

也就是先问：

- 哪些能力一旦成立，系统就算有了第一版正式基线？

而不是问：

- 这个平台未来还可能做什么？

### 2. 用多域 spec 建系统骨架

复杂系统不要硬塞进一份总 spec。

更好的做法是：

- `auth/spec.md`
- `requests/spec.md`
- `approvals/spec.md`
- `notifications/spec.md`
- `audit/spec.md`

### 3. 把系统级骨架决策放进 design

比如：

- 模块化单体还是微服务
- 状态流模型
- 通知异步化
- 审计 append-only

### 4. 把会改变系统性质的新能力留给后续 change

比如：

- 预算联动
- 多级审批
- 外部 ERP 对接

这些不是不重要，而是不该挤进第一个基线 change。

## 和 `11` 对照着看，会更清楚

这两篇其实是在讲 OpenSpec 的两种典型使用场景。

### `11` 的重点

- 已有系统
- 已有正式基线
- 某个局部能力 change
- delta spec 更突出

### `13` 的重点

- 从零开始
- 需要建立第一版正式基线
- 多个能力域一起成形
- design 对系统骨架更关键

所以两者不是重复，而是互补。

如果说 `11` 回答的是：

- "在一座已经建起来的城里，怎么扩建一个新街区？"

那么 `13` 回答的就是：

- "在一片空地上，怎么先把第一版城镇建成体系、但又不过度膨胀？"

## 从零开始最容易踩的 6 个坑

| 坑 | 表现 | 为什么危险 | 正确做法 |
|-----|------|-----------|---------|
| **第一版就想做完整系统** | proposal 里列了 20 个功能模块 | scope 失控，永远做不完第一版 | 只做 MVP，明确 Out of Scope |
| **把全局约束塞进 change** | 在 proposal 里写"所有代码必须 TDD" | 这是项目级原则，不是单次 change 的内容 | 全局约束放 config.yaml |
| **spec 写成实现细节** | spec 里写"用 Redis 缓存审批状态" | 这是技术选型，不是行为合同 | 技术决策放 design，行为放 spec |
| **多域 spec 边界不清** | requests 和 approvals 的职责混在一起 | 后续扩展时不知道改哪个文件 | 每个域有明确的职责边界 |
| **design 太浅** | design 只写"用 TypeScript 和 React" | 没有说清楚系统骨架决策 | 说清楚模块边界、状态流、异步策略 |
| **第一版就想支持所有场景** | 同时做单级审批、多级审批、预算联动 | 复杂度爆炸，无法收敛 | 先做最简单的闭环，后续再扩展 |

### 典型踩坑案例：scope 失控

**错误做法**：
```markdown
# Proposal: Build Procurement Platform

## Scope
- 员工提交采购申请
- 多级审批链（部门经理→财务→CEO）
- 预算中心联动
- 供应商管理
- 采购执行跟踪
- ERP 对接
- 移动端支持
- 国际化
- 报表中心
```

结果：
- 三个月后还在纠结多级审批的路由规则
- 预算中心接口一直没对齐
- 移动端和 Web 端状态不一致
- 永远做不完，永远没有第一版基线

**OpenSpec 做法**：
```markdown
# Proposal: Bootstrap Procurement MVP

## Scope
- 员工创建采购申请
- 主管单级审批
- 审批结果通知
- 审计记录

## Out of Scope
- 多级审批链（future: add-multi-step-approval）
- 预算联动（future: add-budget-policy-gates）
- 供应商管理（future: add-supplier-catalog）
- ERP 对接（future: integrate-erp-export）
```

结果：
- 两周完成第一版 MVP
- archive 后有了正式基线
- 后续每个功能都是独立的 change，可控可追溯

### 如果换一种方式会怎样：不用 OpenSpec

**传统做法**：
1. 产品写一份 50 页的 PRD
2. 架构师画一堆 UML 图
3. 开发开始写代码
4. 做到一半发现需求理解有误
5. 回头改 PRD，但代码已经写了一半
6. 最后代码能跑，但没人说得清系统边界
7. 三个月后加新功能，不知道该改哪里

**OpenSpec 做法**：
1. 先开 change，明确第一版边界
2. 用多域 spec 建立系统骨架
3. design 说清楚关键技术决策
4. 实现过程中发现问题，回头修正 artifacts
5. archive 后有了正式基线
6. 三个月后加新功能，直接看 specs/ 就知道当前系统是什么

---

## 这篇案例最该带走的 10 句话

1. 从零开始不等于一次性定义整个系统未来
2. 第一个 change 的任务，是建立第一版正式基线
3. 复杂系统的第一版边界，必须明确写出 `Out of Scope`
4. greenfield 场景里，常常需要多份域 spec 一起建立系统骨架
5. spec 先定义行为合同，再让设计和实现跟上
6. design 在 greenfield 里往往承担系统骨架决策
7. tasks 必须能承受多人并行，而不只是单人待办
8. scope 一旦引入新角色、新流程、新依赖，通常就该考虑新开 change
9. archive 在 greenfield 里意味着"第一版系统基线正式成立"
10. OpenSpec 能把"从零构建"平滑过渡到"持续演化"
