# 版本细节：v2.0.0 – v2.1.1

> 本文件是 [`answer.md`](../answer.md) 的版本细节附件，记录 **v2.0.0 – v2.1.1** 的逐版提醒。
> 主干（升级步骤、验证、爆炸半径）只在 answer.md 维护，这里不重复。

## v2.0.0–v2.1.1 的具体提醒（来自同步记录 0015）

- **命令文件没了，skills 顶上**：`/opsx:*` 这类 command 文件在 2.0 不再生成。每个命令都有内容等价的技能，对应关系是：

  | 1.x 命令文件 | 2.x 技能 | Claude Code 调用 | Codex 调用 |
  |---|---|---|---|
  | `/opsx:propose` | `openspec-propose` | `/openspec-propose` | `$openspec-propose` |
  | `/opsx:explore` | `openspec-explore` | `/openspec-explore` | `$openspec-explore` |
  | `/opsx:apply` | `openspec-apply-change` | `/openspec-apply-change` | `$openspec-apply-change` |
  | `/opsx:update` | `openspec-update-change` | `/openspec-update-change` | `$openspec-update-change` |
  | `/opsx:sync` | `openspec-sync-specs` | `/openspec-sync-specs` | `$openspec-sync-specs` |
  | `/opsx:archive` | `openspec-archive-change` | `/openspec-archive-change` | `$openspec-archive-change` |
  | `/opsx:new` | `openspec-new-change` | `/openspec-new-change` | `$openspec-new-change` |
  | `/opsx:continue` | `openspec-continue-change` | `/openspec-continue-change` | `$openspec-continue-change` |
  | `/opsx:ff` | `openspec-ff-change` | `/openspec-ff-change` | `$openspec-ff-change` |
  | `/opsx:verify` | `openspec-verify-change` | `/openspec-verify-change` | `$openspec-verify-change` |
  | `/opsx:bulk-archive` | `openspec-bulk-archive-change` | `/openspec-bulk-archive-change` | `$openspec-bulk-archive-change` |
  | `/opsx:onboard` | `openspec-onboard` | `/openspec-onboard` | `$openspec-onboard` |

  注意斜杠写法就是**完整技能名**，不是命令名：`/opsx:apply` 对应的是 `/openspec-apply-change`。`openspec update` 会按已发布指纹自动删除 1.x 生成且未改动过的命令文件，编辑过的保留并列出。
- **也可以不点名**：直接说「帮我 propose 一个 change」，agent 会按技能描述自己选。技能被 agent 自行选中、而项目没初始化时，它会安静放弃 OpenSpec 按普通请求回答；你点名 OpenSpec 时它才会停下来问你怎么做。
- **项目作用域下 skills 只有一份真身**（v2.0.0 #2223）：真身写在 `.agents/skills/`，Claude Code、Continue、ForgeCode、Kiro、CodeBuddy、EasyCode、iFlow、CodeArts、Lingma、GigaCode、Veai、Rovo Dev、Code Studio、Hermes Agent 等在各自 `skills/` 目录建指向它的相对链接（MiniMax Code 例外，落在 `~/.minimax/skills/`）；建不了链接就退化为拷贝。**Windows 两点细节**：①检出已提交进 Git 的 symlink 需要 `git config --global core.symlinks true` 并开启开发者模式，否则链接会检出成文本小文件（`openspec update` 会将其替换为普通拷贝）；② 在 Windows 上跑 `--scope project` 安装技能时，`skill-installer.ts:99` 显式传 `mode: 'copy'`（而非 `'auto'`），因为 Windows junction 无法随 Git 提交带给队友。
- **`delivery` 退役但保留兼容空操作**（v2.0.0 #2223）：OpenSpec 2.0 只装 skills，`delivery` 不再改变任何生成行为；但 `openspec config set delivery ...` 仍被接受并打印 `DELIVERY_RETIRED_NOTE`（`"Note: delivery no longer changes anything; OpenSpec 2.0 installs skills only."`，`src/commands/config.ts:457`），确保 1.x 升级提示里的旧脚本 `openspec config set delivery skills && openspec update` 不会报错中断。
- **Amazon Q Developer 退役**（v2.0.0 #2223）：它读不了 skills。`openspec init --tools amazon-q` 会直接报错并指路 `openspec init --tools kiro`；`openspec update` 通过 `cleanUpRetiredTools` 清理 `.amazonq/` 里未改动的 OpenSpec 生成文件，保留并列出用户改过的文件。
- **v2.0.0 其余两处补丁**：`#2228` 修复 `openspec instructions apply` 读取多行任务（含末尾 `\` 续行）被首行截断的问题；`#2229` 修复 Windows `cmd.exe` 下跑 `openspec completion install` 误改 PowerShell profile 的问题（明确区分 `cmd.exe` 与 PowerShell，且不在 `cmd.exe` 弹补全提示）。
- **全局技能与新默认作用域**（v2.1.0 #2241）：安装层接入 `skills` 包，原生支持 `--scope global | project`：
  - **新项目 `openspec init` 默认 `--scope global`**（交互与非交互均如此；仅 `--tools none`、`--copilot-cloud` 或 `eve`/`promptscript` 例外）。要把技能留在仓库里，需传 `openspec init --scope project`（或设 `OPENSPEC_SKILLS_SCOPE=project` / 全局 `config.json` 的 `skillsScope: "project"`）。
  - **已有项目跑 `openspec update`**：交互终端下若项目已有仓库内技能且未记录选择，会询问「Keep in this project」或「Switch to global」，选前者写入 `openspec/config.yaml` 的 `skillsScope: project`；CI / agent 非交互环境不弹窗，就地刷新。
  - **本机账本与锁文件**：`init` / `update` 会将项目路径记入 `<globalDataDir>/projects.json`（纯本地、读写失败静默忽略、不会自动遍历其他仓库）；全局技能同时写入 `~/.agents/.skill-lock.json`（或 `$XDG_STATE_HOME/skills/.skill-lock.json`，v3 格式），使 `npx skills list/update/remove -g` 可直接识别管理。
- **Node 门槛**（v2.1.0 #2241 起）：npm 包需要 **Node.js 22.20.0+**（v1.16.0–v2.0.0 为 22.12.0+）。standalone 单文件二进制仍不需要 Node。
- **v2.1.1 的全部 9 项修复**：
  1. **#2283（离线从 npm 包安装技能）**：`init` / `update` 直接从已安装的 npm 包写出技能文本（不再需要 Git 或访问 GitHub，离线可用、版本与 CLI 严格一致），且通过 `stripVolatileFrontmatter()` 剥离 `generatedBy:` 行。
  2. **#2269（兼容 `npx skills add`）**：`openspec update` 能发现并刷新此前通过 `npx skills add` 装进项目的技能。
  3. **#2264（Homebrew / Nix 升级识别）**：`openspec version --check` 与 `openspec update` 不再对 Homebrew 或 Nix 安装提示/执行 `npm install -g`；Homebrew 报 `homebrew` 并给 `brew upgrade openspec`，Nix 报 `nix` 且不给 npm 命令。
  4. **#2265（MODIFIED 超长告警）**：当 `MODIFIED` requirement 正文总长度超过 500 字符**且**比主 spec 基线更长（`nextText.length > 500 && nextText.length > currentTextLength`）时发出 WARNING，让 `validate <change> --strict` 在归档前拦住超长扩写（只缩短或未变长的既有长 requirement 不误报）。
  5. **#2273（delta 顶部允许 YAML frontmatter）**：以合法键值开头的顶部 `---` frontmatter 块不再被算作归档丢失散文，`validate --strict` 正常通过；`archive` 将该块留在归档后的 change 中并点名提示。
  6. **#2266（退役能力放行 `<` 开头的折行正文）**：`retire_capabilities` 归档删除 capability 时，requirement 或 scenario 折行后以 `<args>` 这类类标签词开头的普通句子续行不再被误判为块外残留而拒绝退役；真正的原始 HTML 块（如 `<div>`、`<!--`）与独立成行的标签仍会被拦截。
  7. **#2267（新建主 spec 的 `## Purpose` 空行）**：`openspec archive` 创建新主 spec 时在 `## Purpose` 后补齐空行，直接通过 Prettier 与 markdownlint（MD022）。
  8. **#2274（continue 完成后的 apply 交接）**：`openspec-continue-change` 技能在规划产物全部完成后重新提示下一步交给 apply。
  9. **#2277（归档前先检查归档目标目录）**：`openspec-archive-change` 在写任何主 spec 之前先定位已存在的归档目录，避免写完主 spec 才因归档目录问题中断。
