# 问题

Specs 越堆越多之后，喂给 agent 的上下文会**腐化**（无关/陈旧内容挤掉信号）或**漂移**（agent 拿着过期的图景干活）；而敏捷迭代里，**方向本身在来回晃**——开头是这么想的，做下去隔一阵又换了方向，整个项目一直在左晃右晃。

问：**OpenSpec 自带的机制里，对这两件事分别有什么预防手段？边界在哪？缺口在哪？我使用时该注意什么？**

约束条件（本次探究自己加的，很重要）：

- **只认 OpenSpec 自带的能力**——装了 `@fission-ai/openspec` 就有的东西。
- **严格排除三类**：① 上游团队管理自己项目的仓库约定；② 已提案但未落地的能力；③ OpenSpec 维护自己源码用的内部测试与台账。
- 结论必须能在 CLI 实测复现，或能落到 `src/` 的具体行。

# 背景

`_digested/specs_truth/` 与 [`../14_main_specs_context_scaling/`](../14_main_specs_context_scaling/question.md) 已经建立了"主 specs 增长 → 按需读取"的视角，[`../11_keep-specs-aligned/`](../11_keep-specs-aligned/question.md) 讲了"怎么别让 main specs 和代码对不上"，[`../17_review-and-validation-surface/`](../17_review-and-validation-surface/question.md) 拆了"归档前的审阅/校验面"。

本篇换一个切法：不再问"有哪些命令"，而把问题压成**两条正交的线**——

```text
线 A  上下文腐化   规格多了，灌进去的东西变脏     → 答案在"注入什么、怎么读"
线 B  方向漂移     方向变了，产物之间不再自洽     → 答案在"谁判定不一致、谁来拦"
```

这两条线的答案**性质完全不同**，混在一起讲必然失真。而探究过程中还发现第三个必须引入的维度：

```text
硬能力   代码判定，违反就 exit 1 / 拒绝合并 / 丢弃
软能力   随包下发的 prompt 文字，违反什么都不会发生
```

很多看起来像"防漂移机制"的东西，其实只是 prompt 里的一句话。**把软能力当硬能力讲，就是这个题目上最容易犯的错。**

另一个背景是**默认 profile**：开箱拿到的是 `core`，不是全部工作流。这直接决定了"自带能力"的清单有多长。

## 探究过程中的两次转向（值得记下来）

1. **一开始漏掉了自定义 schema 这条杠杆**，结论写成了"方向没有任何机器表示"。review 时实测 `openspec schema init/fork` + 自定义 artifact，发现方向**可以**变成一等 artifact 并接入 DAG 门控——结论因此修正为"内置 schema 没有方向概念，但自带能力里有路给它建门控"。
2. **发现"硬 vs 软"分界比预想的重要得多**。同一批"随包下发"的东西里，一半是代码判定（违反就 exit 1），一半只是 prompt 文字（违反什么都不会发生）。不分开讲，读者会以为工具会拦住他。
