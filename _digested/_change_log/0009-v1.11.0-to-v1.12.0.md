## 核心主题

v1.12.0 的重心是**让 validate 的报告面适应批量场景，并继续补工具生态与工作流引导**：

- **`openspec validate --report findings`** — 大批量校验时只输出有问题的条目，不再是全部条目。
- **validate 把 archive 会拒绝的 delta 合并冲突报为 informational findings** — 冲突在归档前就能看到。
- **SourceCraft Code Assistant** 成为受支持的 adapter-backed 工具（VS Code 扩展）。
- **`openspec init` 为空目录写 `.gitkeep`** — 空 OpenSpec 目录在 Git 里不再消失。
- **init/update 共享 IDE restart 提示** — 同一句话不再维护两份。
- **propose / fast-forward 工作流先读项目代码** — 计划反映现有实现，而不是把发现推迟到实施。
- **explore 的提问改成依赖感知** — 先查代码库，再问 repo 自己答不了的事实。
- **npm git 安装不再需要 pnpm**（`prepare` 用 `node build.js`）、**Node 20 chalk 兼容**、**PowerShell completion 有托管文档**。

## 按领域拆解

### `openspec validate --report findings`（新功能）

| 维度 | 变更 |
|------|------|
| CLI 变更 | `openspec validate --report full\|findings`，且**必须**配显式批量 scope（`--all`、`--changes`、`--specs`、`--archived`）之一；不能带 item name；`archived` 与 active scope 不能混用 |
| 输出语义 | `findings` 只返回有 error/warning/information 的条目；保留全量运行的总数和退出码；默认 `full` 报告不变 |
| JSON 形状 | `projectValidationFindings()` 产出独立 report：`{ report: { kind: 'validation-findings', scope }, ... }` —— findings 是独立报告类型，不是 full 报告的子集 |
| 校验入口 | `BulkValidationResult` 增加 findings 收集；strict/json/noInteractive/concurrency 照常透传 |

**意义**：项目 change 多的时候，`validate` 的 full 报告全是通过条目，findings 报告把注意力收窄到真正要修的东西。依赖影响：`_digested/spec_cli/02-machine-facing-cli.md`（JSON 形状）、`_digested/spec_cli/01-human-facing-cli.md`（命令面）、`_digested/internal-spec-driven/00-四条命令的共有机制.md`（校验入口）。

### validate：archive 会拒绝的 delta 合并冲突 → informational findings

| 维度 | 变更 |
|------|------|
| 新行为 | `src/core/validation/` 的 advisory merge preflight：delta 与 main spec 的合并冲突在 validate 时报为 informational findings，成功文本报告里也会出现，**不改退出码** |
| 错误保真 | 文件系统读取错误保留为 error，不再被误判成「spec 缺失」 |
| 容错 | 预检无法解析输入时，validation 报告保持完整，不被中断 |

**意义**：validate 和 archive 对 delta 的解读从此一致——archive 会拒绝的东西，validate 阶段就亮出来。依赖影响：`_digested/internal-spec-driven/04-archive-归档合并.md`、`_digested/mechanisms/03-spec-model.md`、`_digested/specs_truth/`。
