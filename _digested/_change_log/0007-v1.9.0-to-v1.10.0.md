## 先厘清同步边界

v1.9.0 的资料基线是 tag `2826b88`。本次目标 `upstream/main` 与 `v1.10.0` tag `1ebddd1` 重合，没有 tag 后增量，因此版本边界可以直接写成 `v1.9.0..v1.10.0`。

但 v1.10.0 的 CHANGELOG 不是完整的行为清单。它记录了 `init --language`、completion tip、store-aware main-spec path、archive retirement guidance、tasks verification 和 update restart 等 changeset；同一 commit 区间内的 Zed Agent、no-spec schema 自动 marker、profile/sync 依赖、OpenCode 参数传递、feedback 保真和 telemetry stderr 等实质变化没有全部列入 release notes。本记录以完整 commit range、源码和测试为依据，不只复述 CHANGELOG。

## 核心主题

v1.10.0 的重心是让**非默认语言、store、自定义 schema 和非交互 CLI**这些真实使用场景进入同一套可靠契约：

- 新项目可以用 `openspec init --language` 建立 artifact 语言约束。
- specs artifact 在 store 场景下终于用 `planningHome.root` 读取正确的 main spec。
- tasks 生成契约要求每项工作说明如何验证。
- 无 specs artifact 的自定义 schema 自动获得 `skip_specs: true`。
- capability retirement 的失败路径不再只报一个没有出路的空 spec 错误。
- Zed、OpenCode、custom profile 和 update 的工具投递行为得到补齐。
- npm 安装不再执行 postinstall；completion 与 telemetry notice 都保护 stdout。

## 按领域拆解

### 初始化与多语言：`openspec init --language`

[#1685](https://github.com/Fission-AI/OpenSpec/pull/1685) 新增：

```text
openspec init --language "Portuguese (pt-BR)"
```

新项目会在 `openspec/config.yaml` 的 `context` 中写入：

```yaml
context: |
  Language: Portuguese (pt-BR)
  All artifacts must be written in Portuguese (pt-BR).
  Keep OpenSpec structural headings and SHALL/MUST keywords in English.
```

关键边界：

- 这是新 config 的快捷种子，不是新的 schema 字段。
- 已有 `config.yaml` 或 `config.yml` 时不会覆盖；若同一 language context 已存在则可继续，否则要求用户手工编辑 `context`。
- 值必须非空、单行，不含控制字符、双向控制字符或不可见格式字符。
- 序列化后的 context 受现有 50KB project-context 上限约束。
- 目标 config 不可写或路径不安全时，整个 init 明确失败，不留下“工具生成了、语言配置没写”的半成功状态。
- artifact 正文可以本地化，OpenSpec 结构 heading 和 SHALL/MUST 仍保持英文。

**源码/测试锚点**：

- `src/cli/index.ts`
- `src/core/init.ts`
- `src/core/project-config.ts`
- `test/core/init.test.ts`
- `test/cli-e2e/basic.test.ts`
- `test/commands/declared-store-fallback.test.ts`
- `openspec/specs/cli-init/spec.md`
- `docs/multi-language.md`

**意义**：v1.8.0 允许非英语 requirement 在 normal validate 下工作；v1.10.0 进一步给出创建项目时的正式语言入口，同时保留 parser 所需的英语结构词。

### Specs instruction：main spec 路径必须 store-aware

[#1703](https://github.com/Fission-AI/OpenSpec/pull/1703) 修复内置 `spec-driven` schema 的两处 agent instruction：

1. MODIFIED requirement workflow 读取现有 main spec。
2. 直接修复既有 capability 的 `TBD` Purpose。

旧 instruction 使用 cwd-relative：

```text
openspec/specs/<capability-path>/spec.md
```

现在统一使用：

```text
<planningHome.root>/openspec/specs/<capability-path>/spec.md
```

`planningHome.root` 来自 `openspec instructions ... --json`。它已经解析了显式 `--store`、项目 `store:` pointer、global default store 和普通 repo-local 四种情况；agent 不应再次自行猜测 root。

**边界**：

- 这是 schema instruction 修复，不是 archive/sync CLI 第一次支持 store；后两者早已使用 resolved root。
- 普通 repo-local change 的 root 仍是当前项目，因此兼容旧路径。
- 它解决“读错同名 local capability”或“在 store change 中找不到 main spec”，不提供自动 spec retrieval，也不改变 nested capability 的 namespace 语义。

**源码/测试锚点**：

- `schemas/spec-driven/schema.yaml`
- `test/core/templates/main-spec-paths.test.ts`
- `test/core/templates/propose.test.ts`

### Tasks：每一项必须说明如何验证

[#1660](https://github.com/Fission-AI/OpenSpec/pull/1660) 更新 `spec-driven` 的 tasks instruction：

- 每个 checkbox task 必须在自己的描述中说明 completion verification。
- verification 可以是 test、command、observable behavior 或 delivered artifact。
- 只有覆盖多个 implementation task 的 integration/system verification 才单列独立 task。
- onboard workflow 的生成模板同步采用 `— verify:` 形式。

示例：

```markdown
- [ ] 1.1 创建导出模块，并通过导出单元测试验证公开 API
```

**边界**：这是 schema instruction 和 agent 生成契约，不是 `openspec validate` 新增的硬校验。旧 tasks 文件不会因为缺少 verification 自动 validate 失败。

### 自定义 schema：no-spec change 自动显式化

[#1655](https://github.com/Fission-AI/OpenSpec/pull/1655) 统一 specs artifact 路径判断：

- `specs/**`
- `./specs/**`
- Windows 分隔符形式

如果一个 schema 没有任何 artifact 的 `generates` 落在 `specs/` 下，`openspec new change` 会自动在 `.openspec.yaml` 写入：


- 这是为真正不产生 delta 的 schema 建立显式元数据，不允许行为变化借此绕过 specs。

### Archive：capability retirement 不再进入无解错误

[#1699](https://github.com/Fission-AI/OpenSpec/pull/1699) 修复 retirement 的错误指引。change 移除 capability 最后一个 requirement 后，分三类处理：

| 状态 | v1.10.0 行为 |
|---|---|
| spec 可安全退役，只缺 marker | 提示在 `.openspec.yaml` 加 `retire_capabilities: true` 后重跑 |
| spec 还有 merge 无法解释的内容，如 `## Notes` 或 requirement 外注释 | 列出最多三条 blocking lines；要求迁入 `## Purpose` / canonical requirement，或手工删除 spec；此时不会误导用户先加 marker |
| marker 已声明，但仍有无法安全删除的内容 | 明确说明 marker 已读取但不能被 honor，并列出阻塞内容 |

用户编写的 blocking lines 在进入终端前会清理控制字符，并限制为最多三行、每行最多 200 code points；invalid marker reason 只清理控制字符，不套用 blocking-lines 的行数/长度限制。

**不变边界**：

- `--no-validate` 不触发 capability retirement。
- 重复 `## Requirements` 等可修复结构错误不应被误写成“必须退役”。
- 退役仍会删除整个 main spec，并给出恢复路径。

**源码/测试锚点**：

- `src/core/archive.ts`
- `src/utils/change-metadata.ts`
- `test/core/archive.test.ts`
- `test/utils/change-metadata.test.ts`

### Packaging：移除 postinstall，首次运行再提示 completion

[#1704](https://github.com/Fission-AI/OpenSpec/pull/1704) 删除 npm `postinstall`。发布包不再因为一条 completion 提示触发 `allow-scripts` 警告，也不会让 `npm approve-scripts` 在 global install 中进入 `ENOMATCH`。

新行为由 `src/core/completion-tip.ts` 和 CLI `postAction` 承载：

- 首次适合、且 action 正常返回或只设置 `process.exitCode`、从而真正到达 root `postAction` 的交互式 CLI 运行，在 stderr 提示 `openspec completion install`。
- 只提示一次；已安装 completion 时不提示。
- `CI`、`OPENSPEC_NO_COMPLETIONS=1`、不支持的 shell、JSON run、非 TTY、`completion` / `__complete` 命令不显示。
- JSON/非 TTY 等情况是 defer，不会提前把 tip 标成已看过。
- 状态通过 raw global-config read/write 保存，避免读取默认值后把 `profile: core` 意外写回、破坏旧 profile migration。
- `change validate` 不再提前 `process.exit()`，从而允许 postAction 和 telemetry flush 正常执行；exit code 语义不变。

失败边界也要区分：`process.exitCode = 1` 不会跳过 commander 的 `postAction`，所以 `change validate` 这类失败仍可能显示/消费 tip；多数 action 的 catch 仍调用 `process.exit(1)`，会直接结束进程并跳过 `postAction`，该次失败不会消费 tip，后续真正到达 hook 的 eligible run 才显示。

**边界**：registry install 没有 install lifecycle script；源码/git/directory install 所需的 `prepare` build 仍存在。
