## 同步方式（本次定下的长期约定）

以后不再讨论“怎么 merge 上游”。**历史里已有的 merge 保留不改写**（如 v1.14.3 的 `95b7f247`）；从 v1.15.0 起，新增同步只有 **squash 盖上去**。

- **本地 REPO 与目标 tag 的关系**：所有上游跟踪路径逐字节一致。验收命令：

  ```bash
  git diff --diff-filter=MD <tag> HEAD -- .   # 必须为空；M=修改，D=删除
  ```

- **本地允许的差异只有新增**：`_digested/`、`_faq_on_digested/`、`_openspec_handbook/`，以及根目录的 `CONTEXT.md`（FAQ 术语表，上游没有这个文件）。
- **同步前先确认本地没动过源码——用 diff，不要用 log**：

  ```bash
  git diff --stat <当前基线 tag> HEAD -- src scripts test bin build.js package.json
  ```

  必须为空。`git log <tag>..HEAD -- src …` 不能当判据：历史 merge（如 `95b7f247`）和 squash 提交都不在 tag 的祖先链上，这个 log 永远不空。本次同步前用 diff 验证为空，说明同步前的 272 个本地提交没动过源码；本地改动集中在 `_`、`CONTEXT.md` 和 `.gitignore`。
- **不新增的两件事**：以后再做真正的 `git merge`（会新增 upstream 血缘和 merge commit）`git rebase`（会改写本地提交的 hash）。历史 merge 保留；本地自有内容只在 `_` 与 `CONTEXT.md`，上游从不碰。
- **冲突规则**：共享文件（如 `.gitignore`）一律取上游版本；本地确实需要的忽略项写进 `.git/info/exclude`，不要写进受版本控制的 `.gitignore`。这样下次同步这个文件会干净合入。
- **下次“跟到哪里就用哪里”**：先明确指定目标 tag（例如下一次 `v1.16.0`），然后只 squash 那个 tag。不因为 `main` 有新提交就顺手跟 main，也不因为 npm `latest` 漂移就换目标。

## 本版主题

v1.15.0 是一个 minor：两件新能力，其余是性能、表单对齐和稳健性修复。

1. **免 Node.js 的独立安装**：每个 release 产出 8 个平台单文件，安装脚本校验 `SHA256SUMS` 后落到 PATH；`openspec install` 可以从 npm 等安装方式原地切换到单文件。
2. **`openspec update --dry-run`**：用同一条写入路径预演 update 会新增/修改/删除哪些文件，`--json` 给机器读；不落盘。

## 按领域拆解

### 1. 独立安装：一个文件、不需要 Node.js

| 文件 | 作用 |
|------|------|
| `scripts/binary/entry.mjs` | Bun 编译入口 |
| `scripts/binary/build.mjs` | 用 Bun 把 CLI 编成单文件；Bun 临时文件 `*.bun-build` 被忽略 |
| `scripts/binary/install.sh` / `install.ps1` | 官方安装器：选平台资产、下载、校验 `SHA256SUMS`、安装、必要时改用户 `PATH` |
| `scripts/binary/e2e.sh` / `smoke.sh` / `install-check.sh` | 安装与运行验证 |
| `.github/workflows/binaries.yml` | 8 个目标构建 + 实机验证 + release 资产挂载 |
| `src/commands/install-standalone.ts` | 新增 `openspec install [version]` 命令 |
| `src/core/standalone-tip.ts` | 对全局包管理器用户的一次性提示 |
| `src/utils/executable-path.ts` | 判断 PATH 上第一个 `openspec` 是不是刚装的那个 |

关键行为：

- **8 个资产**：`linux-x64`、`linux-arm64`（glibc 2.17+）；`linux-x64-musl`、`linux-arm64-musl`（Alpine 3.17+，需 `apk add libstdc++ libgcc`）；`darwin-x64`、`darwin-arm64`（macOS 13+）；`windows-x64`、`windows-arm64`（Windows 10+）。每个目标都在对应实机/容器上跑过。
- **`latest` 的取法**：`install.sh` 不直接信任 GitHub 的 `latest` 指针（它会在资产挂齐前就更新），而是找“`SHA256SUMS` 已上传”的最新 release；`SHA256SUMS` 在 workflow 里最后上传，作为“这一版资产完整”的信号。
- **安装位置**：默认 `~/.local/bin/openspec`；Windows 默认 `%LOCALAPPDATA%\Programs\openspec\openspec.exe`。可用 `OPENSPEC_INSTALL_DIR` 改目录、`OPENSPEC_VERSION` 钉版本。
- **`openspec install`**：复用同一套官方安装脚本（脚本从 `main` 拉，默认装最新完整 release，也可传 `1.15.0` 这样的版本），把安装目录/文件名显式传给脚本；装完检查 PATH 上实际生效的是不是新文件，并给出移除旧包管理器副本的命令（npm / pnpm / yarn / bun / volta / brew）。它**不会**自己删旧副本。
- **一次性提示**：全局包管理器安装的用户在 `openspec update` 之后会在 stderr 看到一条提示；非 TTY、CI、项目内依赖、npx、源码运行都不显示；只提示，不自动切换。
- **版本标识**：`openspec version` 会标出 `(standalone)`。
- **文档**：`docs/installation.md` 首段改为“单文件，无需 Node.js”，补 8 平台文件表、手动安装、macOS quarantine / Windows SmartScreen 说明；AI 助手安装提示词改为先查 `openspec --version`、再用 `openspec version --check`。`install.md`、`README.md`、`docs-lab/start/installation.md` 同步改口径。

### 2. `openspec update --dry-run` / `--json`

- **写入接缝**：新增 `src/core/update-plan.ts`（约 440 行）。所有 update 的文件写入/删除收敛到 `UpdateFileOps`；真实运行走 `realFileOps`，dry-run 走 `UpdatePlanRecorder`。预览和真实更新共用同一条生成路径，不是两套描述。
- **计划内容**：`changes[]` 记录 `add` / `update` / `delete`、项目相对 POSIX 路径（项目外文件把 home 折成 `~`）、归属 `tool`；`notes[]` 记录交互式运行会提问的步骤（稳定代号 `legacy-tool-directories`、`legacy-artifacts`）；`failures[]` 记录会失败的工具，但不中断其余计划。
- **输出**：无变化时 `No changes: skills and commands are up to date.`；有变化时 `N file(s) would change:` 逐行列出；另有 `Note:` 与 `Would fail:`。
- **CLI**：`openspec update --dry-run`；`--json` 只能与 `--dry-run` 同用，单独使用报错 `--json is only available with --dry-run.`。
- **测试**：`test/core/update-dry-run.test.ts`（656 行）+ `test/core/update-dry-run.property.test.ts`（355 行，属性测试）。
- **关联重构**：`update.ts`（473 行改动）、`shared-skill-target.ts`、`migration.ts`、`legacy-cleanup.ts` 都改为可记录的写操作。
