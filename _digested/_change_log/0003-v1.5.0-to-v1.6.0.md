# 同步 0003：v1.5.0 → v1.6.0

**日期**：2026-07-21

**hash 范围**：`5956a8e` → `60f720c`

**提交数量**：52

**发布边界**：v1.6.0 tag 是 `e1b51d`（含 v1.6.0-beta.1 预发布）；本记录的范围末端 `60f720c` 是其后的 upstream 快照。

> 这是一条“v1.5.0 → v1.6.0 + release 后增量”的研究记录，不是说 `60f720c` 本身就是 v1.6.0 release。尤其是 nested spec discovery 的 `3fdd2f2` 晚于 v1.6.0 tag，后来随 v1.7.0 正式发布。实际源码合入见 [`0004-v1.6.0-to-v1.7.0.md`](0004-v1.6.0-to-v1.7.0.md)。

## 核心主题

这是一个**质量深化 + 生态扩展**版本。v1.5.0 的 stores 重构奠定了新的架构基础，v1.6.0 在此基础上做了大量修复和打磨——6 个 archive 修复、schema instruction 的语义增强、spec 解析的递归化。同时 agent 生态大幅扩展（8+ 新 agent 支持），并新增了一个关键 workflow：`/opsx:update`（修订 planning artifacts）。

## 按领域拆解

### 新 Workflow：`/opsx:update`（修订 planning artifacts）

| 维度 | 变更 |
|------|------|
| 新模板 | `src/core/templates/workflows/update-change.ts` — `openspec-update-change` |
| 职责 | 修订已有 change 的 planning artifacts，保持 artifact 间一致性。**绝不改代码。** |
| 触发 | 用户在 Explore 中做了决策、apply 中发现 design 问题、或其他需要更新 artifacts 的场景 |
| 流程 | 选 change → `status --json` → 读全部 artifacts → 按需更新 → 检查一致性 → 展示变更 |
| 和 continue 的区别 | `continue` 是按 DAG 创建下一个 artifact；`update` 是修订已有 artifacts |

**意义**：这是对 "iterate to apply-ready" 模式的官方化。我们 `_faq_on_digested/05_iterate-to-apply-ready/` 里描述的 "Explore 审视 artifacts → 发现 gap → 修" 循环，现在有了一个专门的 workflow 来承载修订操作本身。

### Archive 修复（6 个）

| 提交 | 修复内容 |
|------|----------|
| `470f572` | scenario-drift check 支持 multiplicity（多个 change 对同一 spec 的场景漂移检测） |
| `9b70481` | 防止 date prefix 堆叠——已有 `YYYY-MM-DD-` 前缀的 change 不会再套一层 |
| `b419e96` | 已 sync 的 RENAMED delta 不再报错，视为 no-op |
| `7958924` | archive 前 specs 已 sync 时不再失败 |
| `b474f81` | archive template：sync 未完成前不移动 change |
| `a13abea` | validate 拒绝放在 change specs/ 根目录的 delta spec |

**意义**：v1.5.0 引入 stores 后，archive 的 resolution 路径发生了一些未覆盖的边缘情况（跨 store spec 路径、date prefix 堆叠、sync 竞态）。v1.6.0 逐一修复了这些问题。对文档的影响：`09-archive.md` 的行为描述需要更新。

### Schema Instruction 语义增强

| 提交 | 变更 |
|------|------|
| `4fdb2a5` | specs instruction 新增"行为契约"指导——specs 是 WHAT 不是 HOW，不写实现细节 |
| `a313bf1` | design 的 Open Questions 语义收紧——只放真正可延后的未知数；如果问题会改变 specs/方案/tasks，现在就解决 |
| `a313bf1` | tasks instruction 新增检查——写 tasks 前检查 design 的 Open Questions，有未解决的先问用户 |

**意义**：这是一次重要的 **instruction 质量提升**。从前 schema instruction 只说"写 specs"，现在明确说"specs 是行为契约、不是实现方案"。这直接影响 agent 生成 artifact 的质量。对文档的影响：`02-propose.md`、`04-continue.md`、`05-ff.md` 的 instruction 描述可能需要更新。

### Spec 解析改进

| 提交 | 变更 |
|------|------|
| `3fdd2f2` | spec 文件发现改为**递归**——支持嵌套目录结构（`specs/auth/oauth/spec.md`） |
| `18cbf5d` | delta spec 解析时忽略 fenced code block——block 内的 `### Requirement:` 不再被误解析 |
| `9a0dfb5` | 统一 requirement reader，消除多处重复的 markdown 解析逻辑 |
| `a13abea` | validate 拒绝 change specs/ 根目录的 delta spec（必须按 capability 子目录组织） |

**意义**：递归 spec 发现是机制层面的重要变化——以前只支持一级 capability 目录（`specs/<capability>/spec.md`），现在支持任意嵌套。对文档的影响：`internal-spec-driven/` 中 spec parsing 相关章节、`specs_truth/` 中的 spec 目录组织规则。

### Template 行为修正

| 提交 | 变更 |
|------|------|
| `de78c31` | propose/continue/ff：**写完一个 artifact 后，创建下一个之前重新从磁盘读依赖文件**（防止 agent 用内存中的旧版本） |
| `15ef3bc` | sync/archive template：使用 store-aware 的 `planningHome.root` 定位 main specs，不硬编码 `openspec/specs/` 路径 |

**意义**：第一个修复很关键——之前的 template 只说"读依赖"，agent 可能在写完 proposal 后凭记忆写 specs，不重新读 proposal.md。现在 template 明确要求重读。对文档的影响：`02-propose.md`、`04-continue.md`、`05-ff.md` 的 Step 指令需要更新。
