## 核心主题

v1.13.0 的重心是**apply 的门控诚实化与 delta 解析的保真修复**：

- **`openspec instructions apply` 对无 spec delta 的 change 给出警告** — 之前「任务写好了但 spec 没写」的 change 会被当成 ready to implement；现在明确报出缺口和两条出路。
- **apply 报完整缺失链** — 不只是第一跳 `Missing artifacts: tasks`，而是整个 build order 的 `missingPrerequisites`。
- **Parser 三修复** — 重复 section header 只应用一份（#1802）、`*`/`+` 列表标记的 REMOVED/RENAMED 读不出来（#1800）、archive 读取换行的 scenario bullet（#1782）。
- **Archive 保留代码 fence 内的空行** — YAML block scalar、Python、expected-output 样例不再被「整理」。
- **update 检测损坏的 command 文件** — 不再因为 skill 文件版本戳没变就报「All up to date」。
- **init 命名 profile 遗漏的工作流** — 用户能知道还有 `new`/`continue`/`ff`/`bulk-archive`/`verify`/`onboard` 可以加。
- **propose 规划前加载项目上下文**；**guidance 教 agent 用 spec-inventory 读 spec**。
- 仓库工程：`CONTRIBUTING.md`、pnpm overrides 只放 workspace、flake hash 修正。

## 按领域拆解

### apply：无 spec 的 change 不再假装 ready（minor）

| 维度 | 变更 |
|------|------|
| 判定门控 | apply 只按 schema 的 `apply.requires` 门控；`tasks.md` 先于 specs 写好的 change，之前读作 ready，现在 `instructions apply` 报 warning（text + `--json`） |
| 两条出路 | ① 先写 specs；② 声明 `skip_specs: true`（`.openspec.yaml`）——指出 `openspec validate` 本就拒绝这种状态 |
| 不受影响 | 有 specs、声明 `skip_specs`、或仍被自己的必需 artifact 挡住的 change |
| 缺失链 | `collectMissingPrerequisites` 按 build order 收集；`--json` 输出 `missingPrerequisites` 数组；文本输出 `Not created yet, in build order: ...` |
| 补救指引 | 给 CLI 命令（`openspec instructions <artifact> --change <name>`），不再引用 `openspec-continue-change` skill（core profile 不装它） |

**意义**：apply 不再对「spec 缺失」视而不见——这正是 `openspec validate` 会拒绝的状态。依赖影响：`_digested/internal-spec-driven/03-apply-实施执行.md`（apply 门控语义）、`_digested/spec_cli/`（instructions 命令面 + JSON 形状）、`_digested/workflows/06-apply.md`。

### Parser：重复 section header 全部应用

| 维度 | 变更 |
|------|------|
| 数据结构 | `DeltaPlan` 的 sections 从 title-keyed record 改为**按书写顺序的 list**——重复的 `## ADDED Requirements` 不再互相覆盖 |
| 大小写 | 大小写不敏感折叠后的 lookup 返回**所有**匹配 section，而不是第一个 |
| 诊断 | 每个 section 保留自己的行号，重复副本的报错指向正确位置 |
| rename 配对 | `FROM:`/`TO:` 按 section 配对，一份里的 `FROM:` 不会和另一份的 `TO:` 配对 |

**意义**：delta 文件里重复写同一 header（例如 fence 内示例自带的重复）不再静默丢内容。依赖影响：`_digested/internal-spec-driven/04-archive-归档合并.md`、`_digested/mechanisms/03-spec-model.md`。

### Parser：接受全部 CommonMark 列表标记

| 维度 | 变更 |
|------|------|
| 范围 | `## REMOVED Requirements` 的 bullet 形式、`## RENAMED Requirements` 的 `FROM:`/`TO:` 行 |
| 修复 | 之前硬编码 `-`，`*`/`+` 写的删除/改名 delta 完全匹配不到——validate 说 valid、archive 说成功，但需求根本没动 |
| 现在 | `[-*+]` 全部接受；`FROM:`/`TO:` bullet 保持可选；`### Requirement:` header 形式不变 |

**意义**：这是「静默不生效」类 bug——delta 写了但什么都没发生，还显示成功。依赖影响：`_digested/internal-spec-driven/04-archive-归档合并.md`、`_digested/specs_truth/`（spec 失真的又一来源）。

### Archive：代码 fence 内空行保留

| 维度 | 变更 |
|------|------|
| 新增函数 | `collapseBlankRunsOutsideFences` — 只折叠 fence 外的连续空行 |
| 复用 | 与模块内其他结构 pass 共用 `buildCodeFenceMask` |
| 行为不变 | fence 外行为与之前一致：只有真正空行算 blank，纯空格行永不作为折叠边界 |

**意义**：需求里 YAML block scalar / Python / expected-output 样例，archive 每跑一次就被「整理」一次的历史 bug 终结。依赖影响：`_digested/internal-spec-driven/04-archive-归档合并.md`。

### Archive：读取换行的 scenario bullet

| 维度 | 变更 |
|------|------|
| 修复 | `retire_capabilities` 之前拒绝任何「scenario bullet 换行到第二行」的 spec——续行被当成无法归属的内容 |
| 覆盖 | `+` 列表标记也被正确识别（之前只认 `-`/`*`，`+` 写的 scenario 全部报 unaccounted，capability 完全无法退役） |

**意义**：包裹换行的 bullet 不再挡住 capability 退役，并恢复提示命名 marker。依赖影响：`_digested/internal-spec-driven/04-archive-归档合并.md`、`_digested/specs_truth/`。

### update：检测损坏的 command 文件

| 维度 | 变更 |
|------|------|
| 之前的洞 | 只比对 skill 文件的 `generatedBy` 版本戳——skill 是新的就报「All up to date」，但旁边手改/截断的 command 文件完全没被检查 |
| 修复 | update 现在也比对 command 文件内容（`--force` 之外的新路径），用本来就存在但从没被 consult 的比较 |
| 边界 | 只针对「skills + commands 都配置」的工具；commands-only 投递路径不变 |

**意义**：`openspec update` 声称 up-to-date 时，项目里的文件真的和模板一致。依赖影响：`_digested/workflows/12-update.md`、`_faq_on_digested/16_upgrade-openspec-cli-and-projects`。

### init：命名 profile 遗漏的工作流

| 维度 | 变更 |
|------|------|
| 新增 | `formatOptionalWorkflowsNote(installedWorkflows)` — 返回 profile 没装的 workflow 名单，全装了返回 null |
| 接入 | `init` 和 `update` 输出里列出：`new`、`continue`、`ff`、`bulk-archive`、`verify`、`onboard` 可加（`openspec config profile`） |
| 意义 | 没装的命令不再读起来像「setup 坏了」 |

**意义**：init/update 的输出把「还存在什么」讲清楚。依赖影响：`_digested/workflows/12-update.md`、`_digested/mechanisms/02-tool-delivery.md`。

### propose：规划前加载项目上下文

| 维度 | 变更 |
|------|------|
| 行为 | `propose` 规划前加载所选项目/store root 的 context，遵守 config 优先级与验证上限 |
| 无 root | 不写任何文件就停止，并建议初始化——不再隐式创建 root |

**意义**：propose 的 plan 有项目事实垫底（与 v1.12.0 的「先读代码」呼应）。依赖影响：`_digested/workflows/02-propose.md`。

### guidance：spec-inventory verb

| 维度 | 变更 |
|------|------|
| 背景 | `openspec list --specs` 出现在任何生成的 skill/command/artifact 指令里；agent 被要求「先读现有 specs」时却枚举了 changes |
| 修复 | explore skill 与 command 同时列出 spec inventory 与 change list 并区分二者；proposal/specs 指令里「研究现有能力」「delta 路径匹配现有 spec」两步带 `--store "<id>"`；capability 读取用 `openspec show "<spec-id>" --type spec --json --no-scenarios` |
| 边界 | filtered read 只是概览；agent 决策前仍需读完整 spec（含 scenarios） |

**意义**：agent 按指令「读 specs」时真的读到 specs。依赖影响：`_digested/workflows/01-explore.md`、`_digested/spec_cli/`、`_digested/mechanisms/04-workflow-templates.md`。
