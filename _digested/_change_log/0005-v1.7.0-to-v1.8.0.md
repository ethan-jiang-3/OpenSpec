## 核心主题

v1.8.0 的重心是**工具投递的收敛与校验/归档的可靠性**：

- 新引入 **vendor-neutral `agents` 目标**（`.agents/skills/`），Codex 的 skills 也迁入同一个共享根目录，并用 ownership marker 解决多目标共享同一目录时的写入归属。
- **GitHub Copilot** 进入一等公民支持：本地 skill + 可选的 cloud coding-agent 文件（`copilot-setup-steps.yml` / `.github/agents/openspec.agent.md`），cloud 文件是 **opt-in**。
- 归档支持 **`retire_capabilities`**：change 删掉一个 capability 的最后一个 requirement 时，可声明 marker 让 archive 删除整个 main spec。
- `openspec status` 区分 **planning 完成** 与整体进度（`isPlanningComplete`）。
- validate 的两个放宽/加强：normal 模式下 SHALL/MUST 变成 guidance（非英语 spec 也能过）；同时前置检测 MODIFIED requirement 会丢 scenario 的情况（以前只在 archive 拒绝）。
- archive 在无法交互提问时给出**可粘贴的重跑命令**，而不是抛一个 agent 无法消化的错误。

## 按领域拆解

### 工具投递：vendor-neutral `agents` 目标与 Codex 迁移

| 事实 | 机制 | 对本仓库的意义 |
|---|---|---|
| 新增 `--tools agents` | `src/core/config.ts` 的 `AI_TOOLS` 增加 `agents`（skillsDir `.agents`，detection 只看 `.agents/skills`） | AGENTS.md 兼容的 assistant 现在有一个共享、宿主中立的 skills 落点；`--tools all` 会创建 `.agents/skills/`。 |
| Codex 迁到 `.agents` | `codex` 的 `skillsDir` 从 `.codex` 改为 `.agents`，`legacySkillsDirs: ['.codex']`，update 时原地迁移并保留用户定制文件 | 旧文档里"Codex 写 `.codex`"的当前结论失效，需要改。 |
| 共享根目录的 ownership 归属 | `src/core/shared-skill-target.ts` 用 `.openspec-target` marker 记录谁在写这个共享根；没有 marker 时按已生成文件的 invocation 语法推断 | `.agents` 同一物理目录现在可能同时被 `agents` 与 `codex` 目标使用，但同一时刻只有一个 active writer。 |

新增工具：**MiniMax Code**（global skills-only，`.minimax`）、**Atlassian Rovo Dev CLI**（skills-only，`.rovodev`）、**GitHub Copilot**（见下）。

### GitHub Copilot：本地 skill + opt-in cloud coding-agent

- `--tools github-copilot` 生成 Copilot 本地 skill。
- **cloud coding-agent 文件是 opt-in**：默认 No，`openspec init` 会先问（`--copilot-cloud` / `--no-copilot-cloud` 非交互指定），选择记入 `openspec/config.yaml` 的 `githubCopilot.cloudAgent`。
- 生成的文件：`.github/workflows/copilot-setup-steps.yml`（预装 CLI）+ `.github/agents/openspec.agent.md`（定制 agent，向 Copilot coding agent 说明如何用 CLI）。
- `openspec update` 从不提示：只刷新已 opt-in、或已存在 managed cloud 文件的旧项目；用户自己改过的文件永不覆盖/删除，opt-out 只删除 managed 文件。

### Archive：`retire_capabilities` 与交互失败时的可重跑命令

- `retire_capabilities: true`（`.openspec.yaml`，与 `schema:` 并存）：change 的 REMOVED 条目拿掉某 capability 最后一个 requirement 时，archive 删除该 capability 的 main spec，而不是以 "Spec must have at least one requirement" 中止。没有 marker 时行为不变，只是错误信息会指明 marker 作为出路。
- 退役只发生在该 spec 本来就无法保留的场景；archive 输出会列出被删的 section，并给可粘贴的 `git checkout` 恢复命令。`--no-validate` 永不触发退役。
- archive 现在拒绝 main spec 中存在重复的 canonical requirement 名。
- 退役前要知道：另一个 in-flight change 的 MODIFIED 块若以该 capability 为 base，会 validate 通过、archive 拒绝（"target spec does not exist"）——需要与退役一起处理。
- archive 在无法交互提问（stdin closed，agent 场景）时，报告需要哪个 flag 并给出**携带原 flags 的可粘贴重跑**（如 `openspec archive <name> --skip-specs --yes`），并修正了无 change 名时 exit 0 吞错误的旧行为（现在 exit 1 请求 change 名）。
- archive 在重建 spec 会丢失 requirement 旁的 note 时先说明会删什么、移到哪。

### Status / 进度：planning 与实现分离

- `openspec status` 的 JSON 新增 **`isPlanningComplete`**：所有非 skipped planning artifact 都存在才算 planning 完成；skipped artifact 视为已满足而不必写出。`isComplete` 保留为兼容别名。
- 状态文案不再在 change 实现前就暗示"已完成"。规划 artifact 的进度与实现进度分开表达。
- task-progress 现在按**缩进子任务**计数（`src/utils/task-progress.ts` 共享 parser）：`list`、`view`、`instructions apply`、`archive` 对同一 tasks 文件的判断一致。

### Validate：SHALL/MUST 放宽 + scenario-loss 前置

- **normal 模式**下，英文 SHALL/MUST 约定是 guidance 而非硬性错误（缺失给 WARNING，消息变成 "should contain"）；其他语言的 requirement 可以 validate。**strict 模式**继续强制约定。见 `src/core/validation/validator.ts` 的 `strictMode` 分支与 `guidanceOnly`。
- **scenario-loss 前置检测**：`validate <change>` 现在会检查 MODIFIED requirement 是否省略了 main spec 仍有的 scenario——archive 本来就拒绝这种 loss，现在 authoring 阶段就失败，失败信息会指名要抄回的 scenarios。见 validator 的 MODIFIED 检查与 `options.mainSpecsDir` 路径。
- **ambiguous task numbering 警告**：`## N.` 分组内的任务编号若引用歧义会告警（tag 后提交 `e50bd09`）。

### 其他

- **`telemetry.enabled`** 在 global config 生效：`false` 关闭匿名遥测与 `openspec update` 版本检查；unset 保持开启；env/CI opt-out 仍优先。
- **propose 保持聚焦 planning**：澄清 material ambiguity 后再建 change，实现交给 apply workflow。
- **explore 转 change 的 guidance**：要求 agent 先 `openspec new change` 再写 artifacts（保住 `.openspec.yaml` 元数据），capture 后不再需要额外命令就能建出 artifact。
- **legacy cleanup 修复**：init/update 不再误删刚生成的 CoStrict / Junie command 文件。
- **security boundaries**：generated files、specs、archive moves、local state 保持在预期边界内，不破坏 linked monorepo 工作流。
