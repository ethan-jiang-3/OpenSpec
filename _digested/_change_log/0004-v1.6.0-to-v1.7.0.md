## 先厘清同步边界

`0003` 的材料研究范围已经看到 `60f720c`，但当时本 checkout 的实际 TypeScript 仍停在较早版本。因此，`0004` 不只是“多写一份 release note”：它让此前只在消化材料里讨论过的行为真正进入本地 `src/`。

其中最重要的一点是：`3fdd2f2` 的 recursive spec discovery 虽然发生在 `60f720c` 之前，却随 v1.7.0 正式发布并在本次 merge 后成为本仓库源码的一部分。`openspec/specs/<domain>/<capability>/spec.md` 现在可被 list/show/validate/parse/apply/archive 一致处理；能力 ID 是相对路径，例如 `identity/session`。它仍是 namespace，不是带继承语义的父子 spec 树。

## 核心主题

这次 v1.7.0 的重心是把“agent workflow 指令”和“确定性 CLI 状态”做得更可靠：零 delta change 有显式语义，archive/sync 不再产生竞态或重复写入，apply/archive 可以获取运行时 project context，同时工具适配从假定 Claude 语法转向按宿主实际调用面生成。

## 按领域拆解

### Nested main specs 已成为可用的发布能力

| 事实 | 机制 | 对本仓库的意义 |
|---|---|---|
| 任意深度的 `spec.md` 会递归发现 | `src/utils/spec-discovery.ts` 统一产生 slash-separated capability ID | 可以用 `identity/session`、`billing/invoices` 分片，而不再只有 flat capability。 |
| change delta 与 main spec 保持同一路径 | archive/apply 用 capability ID 重建 `openspec/specs/<id>/spec.md` | nested delta 不会再被静默跳过。 |
| 核心 CLI 走同一发现器 | list、show、view、validate、change parser、sync、archive/apply 都覆盖 | 这是生命周期支持，而非仅能把文件放进子目录。 |

默认 schema 和 workflow 文本仍多写作 `specs/<capability>/spec.md`；[Issue #1459](https://github.com/Fission-AI/OpenSpec/issues/1459) 仍在追踪 agent-facing guidance 与 runtime 的不一致。因此，大项目采用 nested layout 时仍应在 `config.yaml` / AGENTS 里明确 `<domain>/<capability>` 约定，不能期待默认 agent 自动选对 domain。

### Change 可以合法地没有 delta spec

[#1399](https://github.com/Fission-AI/OpenSpec/pull/1399) 加入 `.openspec.yaml` 的 `skip_specs: true`。纯重构、工具或文档工作可以显式声明没有 spec-level 行为变化；validate 接受零 delta、artifact graph 不再阻塞 tasks，status 会显示 specs 已跳过。

这避免了过去为了通过机械校验而虚构一条需求；但 marker 与任何 delta spec 同时出现会报错，不能拿它绕过真实的行为变更。

### Archive / sync 的正确性显著增强

- [#1431](https://github.com/Fission-AI/OpenSpec/pull/1431)：新 capability 的 delta 可带 `## Purpose`，archive 将它写入新 main spec，不再总是留下 `TBD` 占位。
- [#1437](https://github.com/Fission-AI/OpenSpec/pull/1437)：已被同步掉的 REMOVED requirement 视为 no-op 并给 warning，避免无意义失败和文件重写；RENAMED/REMOVED 冲突被显式拒绝。
- [#1475](https://github.com/Fission-AI/OpenSpec/pull/1475)：delta/main-spec parser 支持 BOM，archive 的 scenario-drift 检查忽略 fenced code；此前通过 validate 却 archive 失败的一类差异被消除。
- v1.7 release 同时收束了 archive 与 sync 的时序：必须完成并核对 spec sync 才能移动 change，避免“change 已 archive、main specs 没写入”的竞态。

这些改动提高 archive 的可信度，但没有引入 spec-code 语义对账、稳定 requirement ID 或 capability rename；长期治理的边界没有消失。

### Runtime context 终于进入 apply / archive 指令面

[#1062](https://github.com/Fission-AI/OpenSpec/pull/1062) 将当前项目 context 和按操作 guidance 扩展到 apply / archive：

```yaml
operations:
  apply:
    guidance: Keep migration steps reversible.
  archive:
    guidance: Confirm compatibility evidence before archiving.
```

`openspec instructions apply` 和新的只读 `openspec instructions archive` 会给相应 workflow 输入。它适合放小而稳定的全局约束，**仍不是**对本地 main specs 的 catalog、语义检索或自动加载。

### Agent / tool 交付从“假定 slash command”转为实际调用面

- Codex 现在是 skills-only：生成 `$openspec-*` skills，旧的 managed custom prompts 在 update 时清理；不要再把 `/opsx:*` 当作 Codex 的默认调用方式。
- [#1471](https://github.com/Fission-AI/OpenSpec/pull/1471) 让每个 adapter 使用它真正注册的命令名，避免生成文件与提示用户输入的命令不一致。
- 模板去除了 Claude 专属的 `AskUserQuestion` / `TodoWrite` 假设，改为 tool-neutral 的 ask-user / todo guidance。
- 新增 CodeArts、Hermes、ZCode 支持，Windsurf 更名为 Devin Desktop；workflow skills 也可作为静态 `SKILL.md` 发布到 skills.sh。

### CLI / UX / store 变化

- `openspec update` 能检测落后的全局 CLI，并在交互式 npm 安装场景提供升级到最新发布版的确认；这正好暴露“源码 checkout 已更新”与“PATH 中二进制仍旧”的区别。
- `openspec new change` 接受数字前缀，如 `100-add-feature`；status 按 schema artifact 顺序展示；只有一个 active change 时 workflow 会自动选择它。
- 上游还补强 global default store、store pointer 的 view resolution、配置键防 prototype pollution、shell completion 和无动画 welcome 等稳定性细节。

## 验收基线

完成同步后，应至少确认：

```text
git describe --tags --always --long     # v1.7.0-... 的本地 merge
node -p "require('./package.json').version"  # 1.7.0
openspec --version                      # 当前环境：1.7.0
```

最后一条不会由 git merge 自动改变；当前环境已通过独立升级达到 v1.7.0，可使用 PATH 中的 CLI 创建或 archive nested capability path。其他机器若仍低于 v1.7.0，应先按既有安装方式升级全局 CLI。
