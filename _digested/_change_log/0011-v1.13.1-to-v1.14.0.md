### apply / archive 正确性（本轮最重要的语义变化）

| 变更 | 提交 | 行为 |
|------|------|------|
| apply 任务源定位 | `e7a951d` | `instructions apply --json` 每个任务带 `sourcePath` + 1-based `line`（`LocatedTask`/`parseLocatedTasks`，不改任务解析本身）；apply 工作流：在该位置勾选 → 标记完成 → 重查进度 |
| **archive 阻塞语义** | `0ff63dba` | workflow 模板（archive-change/bulk-archive-change）：sync 报任何 stop/blocking → **视为 sync 失败，立即停止归档**，不做 post-sync 内容比对、不移 `changeRoot`；一切未动，用户可修复后重跑 |
| sync 后结构验证 | `0ff63dba` | 主 spec 不得残留 `## ADDED/MODIFIED/REMOVED/RENAMED Requirements`；REMOVED 的 requirement 必须已删；retire 掉的 capability（最后一个 requirement 被移除、`## Requirements` 变空）其主 spec 被删除而非留空 |
| inline sync 的时序约束 | `0ff63dba` | 模板明确：不得把 sync 委托后台——step 5 会把 `changeRoot` 移走，留下"已归档但主 specs 没更新"的状态；只能同步等待 |
| Windows EPERM/EXDEV 回退 | `ba0f5087`(v1.13.2 系) | `archive.ts` +409 行：staging rename 遇 EPERM/EXDEV 改走 `copyThenRemoveDirectory`（源→dest 复制再删），fingerprint 检测复制窗口内的写入中断；`captureSpecSnapshots`/`restoreSpecSnapshots` 支持回滚；非 EPERM/EXDEV 的 staging 失败仍保持源不动 |
| 回滚剪裁 | `f2812f62`(v1.13.2) | 新建 spec 的回滚只删自己创建的 capability 目录；已存在的空目录保留 |
| CRLF 保持 | `1d35e908`(v1.13.2) | 新模块 `src/utils/line-endings.ts`：`detectLineEnding`（dominant 判定，CRLF 平局胜出）/`applyLineEnding`/`matchLineEnding`；specs-apply 写回时 `matchLineEnding(rebuilt, previous)`——**只有文件不存在时才写 LF**。同一机制覆盖 completions 安装与 `removeMarkerBlock` 的 blank-line collapse |
| artifact 输出 glob | `fd56e12`(v1.13.2) | `artifact-graph/outputs.ts`：认 brace expansion 与 extglob，同时保留字面量文件名；brace 展开路径限制在 change 目录内 |
| `.openspec.yaml` 未知键 | `88692b3b` | `CHANGE_METADATA_KNOWN_KEYS` 白名单（schema/created/goal/affected_areas/initiative/skip_specs/retire_capabilities）；未知键 status/validate/archive 均告警，`validate --strict` 失败（**注意**：`--strict` 对超长 requirement 失败是 tag 后 main 的 #2020，不属于本版） |

### verify 模板重写（v1.13.2/1.14.0，+167 行）

- verify 不再自己解析 checkbox：改用 status 顶层 `tasks`/`progress`（已聚合 apply.tracks 的所有具体文件）与 `taskTrackingConfigured`。
- **Not applicable 语义**：schema 未定义的检查、status 报告为 intentional skip（`skip_specs: true`、可选 design、无任务追踪的 schema）→ 标 Not applicable，不算失败。
- `apply` 的 `state`/`instruction` 只是 context 不是 verdict；验证是 advisory 的。
- `unavailableTrackingFiles` 非空 → Task Completion 记 not verified 并列出每个不可读路径及原因。
- 提示列表显示所有 active changes（含 `status: "no-tasks"`），不再只显示有 tasks artifact 的。
