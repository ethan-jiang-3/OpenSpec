## 1. 指纹库与旧产物清扫（1.17.0 #2213）

### 数据规模

| 项 | 值 |
|---|---|
| `src/core/shared/released-generated-fingerprints.ts` | **4010 行**（自动生成，勿手改） |
| 内容指纹条目 | 2867 条（16 位 hex） |
| 项目相对路径条目 | 1130 条 |
| 覆盖发布版本 | **42 个**：0.12.0 → 1.16.1 |
| 未覆盖 | 0.1.0–0.11.0（14 个版本，那时还没有非交互式 `init`） |

### 它是怎么造出来的

`scripts/capture-released-fingerprints.mjs`：

1. 对 npm 上列出的每个版本，把那个版本装进缓存目录
2. 用**一次性 `HOME`** 在临时项目里跑 `init --tools all`——每个 profile、每个旧默认 workflow 集、每个该版本支持的 `delivery` 各跑一次
3. 给出现的每一个文件算指纹
4. 重写 `released-generated-fingerprints.ts`

脚本头部写明用途：**「让 `openspec update` 能区分『某个旧版本留下的未改动文件』和『用户改过的文件』」**，并要求每次发版后重跑。

### 指纹怎么算（`src/core/shared/generated-fingerprint.ts`）

关键是**先归一化再哈希**，否则每次发版指纹都会变：

- 去掉 BOM、把 CRLF 折成 LF（checkout 差异）
- 把 YAML frontmatter 里 `generatedBy:` 的**合法版本号**替换成 `<generated-version>`（发版差异）
- 然后 sha256 取前 16 位

所以「因为升级而导致文件不同」不会让指纹失效，**只有人真改过才算不同**。`generatedBy` 里的自由文本仍然算实质内容，不抹。

有个实现细节值得记：匹配缩进用 `[ \t]` 而不是 `\s`，注释说明了原因——`m` 锚定的 `\s*` 会从每一行行首重新扫描，在空白密集的 frontmatter 上是二次方复杂度。

### 清扫怎么判（`src/core/released-output-sweep.ts`）

文件头把意图写得很清楚：找**当前版本根本不会写**的路径上、内容仍是某历史版本原样输出、**且该工具当前的替代产物已经就位**的文件才删。

理由：这种文件既没有用户内容，也不做替代品做不到的事；不清掉就会永远躺在项目里，通常还是同一套工作流的第二份陈旧副本。

## 2. 命令文件弃用（1.17.0 #2213，2.0 的前奏）

### 能力模型（`src/core/command-surface.ts`）

每个工具被归为三种能力之一：

| 能力 | 含义 | 例子 |
|---|---|---|
| `adapter-backed` | 有命令适配器，能生成命令文件 | Claude Code 等 |
| `skills-invocable` | 没有命令适配器，但能用 skills 调用 | `codex`、`warp` |
| `none` | 两者都没有 | — |

四个判定函数由 `delivery` × 能力矩阵驱动：`shouldGenerateSkillsForTool`、`shouldRemoveSkillsForTool`、`shouldGenerateCommandsForTool`、`shouldReconcileCommandFilesForTool`。

### 提示文案（每次 `update` 只要还配着命令文件就提示）

```
Command files are deprecated and go away in OpenSpec 2.0. Your OpenSpec skills stay and do the same work.
  Switch now: openspec config set delivery skills && openspec update
  This removes only the command files OpenSpec generated; any you edited are kept and listed.
  Details: https://github.com/Fission-AI/OpenSpec/issues/2022
```

`update.ts` 的注释解释了时机设计：`update` 是在升级时跑的，所以这条能在大版本删除前触达用户，**又不会天天唠叨**。

### 1.17.0 同时保证的两件事

- 切到 skills-only **不再删除用户编辑过的命令文件**：只删 OpenSpec 生成的，改过的保留并列出来
- 升级过程中**永不碰项目外的文件**

> **对资料的含义**：这是**预告**，不是已经删。2.0 才真正移除。资料里讲 `/opsx:*` 的地方要加时间线注记，**现在不要改口径**。

## 3. validate 三条收紧

| PR | 变化 | 严重级别 |
|---|---|---|
| #2079（1.16.0） | `Scenario:` 没有 WHEN/GIVEN 触发步，或没有 THEN 结果步 | **WARNING**；普通 `validate` 与 `archive` 不受影响，`--strict` 失败 |
| #2207（1.16.1） | requirement 落在 `## DEPRECATED Requirements`、`## Add Requirements` 这类「读起来像 delta 操作、但不是四个合法段」的标题下 | **ERROR**；`validate` 报错，`archive` 拒绝 |
| #2127（1.16.0） | `openspec/config.yaml` 读不了或 YAML 解析失败 | `validate` **退出 1**；其他命令仍只警告继续 |

三点补充说明：

- **#2079 覆盖 delta 与主 spec 同一套检查**：走同一批 `#### ` 块，所以「什么都不断言」的场景在哪个位置都会被报出来。只写 AND 行或纯散文**仍然算场景**，但会被标警告
- **#2207 以前是「警告 + 静默丢掉那条 requirement」**，现在失败。但 `## Notes`、`## Behavior` 这类散文段下的孤立 requirement **仍是警告**——区别在于标题读起来是否像 delta 操作
- **#2127 只让 `validate` 硬失败**，因为 CI 需要一个地方拦住坏 config。JSON 输出里 code 是 `unreadable_config` / `unparseable_config`

配套：`schemas/spec-driven/schema.yaml` 加了一行 WHEN/THEN 要求，写明「普通校验仍通过，`--strict` 失败」。

## 4. 解析器健壮性

- **#2205（1.16.1）CommonMark 闭合 `#` 号**：`## Purpose ##` 与 `## Purpose` 等价；`### Requirement: Foo ###` 的 requirement 名是 `Foo`。`stripClosingSequence` 只在 `#` 前有空格/制表符时才剥（所以 `C#` 保留 `#`；用 `[ \t]` 而非 `\s` 是为了不让 NBSP 分隔的 run 被剥）
- **#2133（1.16.0）**：`###Requirement:`（**没有空格**）现在也会被主 spec 结构检查按 `archive` 的读法匹配，报重复或位置错误
- **#2131（1.16.0）**：行内三反引号（```` ```npm test``` ````）不再被当成代码围栏开头。以前这一行会把**之后所有 requirement 都藏起来**
- **#2207 配套**：HTML 注释与围栏内示例都被 mask，注释掉的草稿不会被报成「丢了一个 requirement」

## 5. `version --check` 语义修正（1.16.1）

- **#2204 显式 `--check` 不受遥测开关与 CI 影响**。用户主动要这一下，只有 `OPENSPEC_NO_UPDATE_CHECK` 和测试守卫还能挡。`update` 的后台检查**仍然**尊重 telemetry opt-out 与 CI
- **#2206 standalone 只提供真能装的版本**。按 `install.sh` / `install.ps1` 的找法：releases atom 源里稳定 tag 从新到旧，找第一个 `SHA256SUMS`（最后上传）存在的。

  npm 的 `latest` 不能当答案：它比 GitHub 资产早几分钟发布，资产 job 失败就永远没有。提供装不上的版本会让 `openspec install` 悄悄重装回旧版。

- **实现细节**：HTTP 从 `fetch` 换成 `node:http(s)`。注释写明原因——abort 一个还在 TCP 握手的 `fetch`（防火墙丢包、强制门户）会留下连接句柄，CLI 退不出去，比提示本身还久。

## 一条踩过的坑（写给下一步）

第一次尝试直接 `git merge --squash @fission-ai/openspec@2.1.1` 时，**合并基点是 1.14.3 而不是 1.15.0**（因为 1.15.0 那次也是 squash，没有 upstream 血缘）。

后果：git 用错基准做三方合并，除了 41 处冲突，还有 **1 个文件自动合并后静默偏离 tag**（`test/core/shared-skill-target.test.ts` 多出一段 2.1.1 里没有的测试）。

所以每次同步必须执行**两步验收**，只看冲突数为 0 是不够的：

```bash
git diff --name-only --diff-filter=U          # 冲突必须为 0
git diff --diff-filter=MD --cached <tag>      # 自动合并漂移；必须为空
```

本次 1.17.0 没有出现自动合并漂移，但 2.1.1 那次出现过，第二步务必复查。
