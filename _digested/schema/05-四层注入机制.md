# 05 · 四层注入机制

> 回 [导读](00-map.md)

OpenSpec 不是简单地把一个 prompt 扔给 AI。它通过 **context → rules → instruction → template** 四层精准叠加，控制 AI 在不同阶段的行为。理解这四层，你才能真正驾驭 schema。

> 注：本文只解释注入给 AI prompt 的四层，所以只展开 `config.yaml` 里的 `context` / `rules`。项目级 `openspec/config.yaml` 的完整有效顶层字段还包括 `schema`，它负责 workflow schema 选择，不属于 prompt 注入层；细节见 `../internal-spec-driven/06-config-yaml-机制与约束.md`。

---

## 总览

```text
┌──────────────────────────────────────────┐
│           最终注入给 AI 的 Prompt           │
├──────────────────────────────────────────┤
│  4. template     ← 输出骨架（Markdown）     │
│  3. instruction  ← 制品专属指令（schema）    │
│  2. rules        ← 按制品匹配的规则（config） │
│  1. context      ← 全局背景（config）        │
└──────────────────────────────────────────┘
```

越靠下越全局，越靠上越具体。每一层都在上一层的基础上**叠加**（additive），而非替换。

---

## 第 1 层：context（全局背景）

**来源**：`openspec/config.yaml` → `context` 字段

**作用范围**：所有 artifact，所有 workflow 阶段

**注入形式**：`<context>...</context>` 包裹的纯文本

**最佳实践**：

```yaml
context: |
  Tech stack: TypeScript, React, Node.js
  Testing: Vitest + Playwright
  Deployment: Vercel
  Public APIs should remain backward compatible.
```

特征：
- **稳定**：不是只对一个 change 成立
- **高价值**：agent 经常需要但不应每次重复输入
- **不替代 spec**：给背景，不定义正式 requirement

**它的限制**：最大 50KB。

---

## 第 2 层：rules（按制品匹配的规则）

**来源**：`openspec/config.yaml` → `rules` 字段

**作用范围**：按 artifact `id` 精确匹配

**注入形式**：`<rules>...</rules>` 包裹的规则列表

**示例**：

```yaml
rules:
  proposal:
    - Include rollback plan
    - Identify affected teams
  specs:
    - Add unhappy-path scenarios for validation and permission failures
    - When modifying behavior, prefer MODIFIED over vague ADDED text
  design:
    - Explain migration risk when storage schema changes
  tasks:
    - Include verification tasks and test updates
    - Keep each task small enough for one focused session
```

**关键规则**：
- `rules` 是 additive，不会替换 schema 内置的 `instruction`
- 只会注入匹配当前 artifact id 的规则
- 未知的 artifact id 会产生 warning（不报错）
- 不适合放工作流结构变更（比如"跳过 design"）——那应该改 schema

---

## 第 3 层：instruction（制品专属指令）

**来源**：`schemas/<name>/schema.yaml` → `artifacts[].instruction`

**作用范围**：仅当前 artifact

**注入形式**：作为 AI 提示的核心指令部分

**示例**（spec-driven 的 proposal instruction 节选）：

```yaml
instruction: |
  Create the proposal document that establishes WHY this change is needed.
  
  Sections:
  - **Why**: 1-2 sentences on the problem or opportunity.
  - **What Changes**: Bullet list of changes.
  - **Capabilities**: Identify which specs will be created or modified.
  - **Impact**: Affected code, APIs, dependencies, or systems.
  
  IMPORTANT: The Capabilities section is critical. It creates the contract
  between proposal and specs phases.
```

**instruction 是 schema 的核心价值**——它定义了 AI 在这个 artifact 阶段"应该怎么想、怎么写"。不同 schema 的差异化主要在这里。

---

## 第 4 层：template（输出骨架）

**来源**：`schemas/<name>/templates/<artifact>.md`

**作用范围**：仅当前 artifact 的输出格式

**注入形式**：`<template>...</template>` 包裹的 Markdown 内容

**示例**（proposal.md 模板）：

```markdown
## Why

<!-- Explain the motivation for this change. -->

## What Changes

<!-- Describe what will change. -->

## Capabilities

### New Capabilities
- `<name>`: <brief description>

### Modified Capabilities
- `<existing-name>`: <what requirement is changing>

## Impact

<!-- Affected code, APIs, dependencies, systems -->
```

**模板的作用**：
- 给 AI 提供输出格式的起点
- HTML 注释是给 AI 看的提示（最终文档中用户可能删除它们）
- 定义了"这个 artifact 产出物长什么样"

---

## 四层叠加实战示例

假设项目配置和 schema 如下：

```yaml
# config.yaml
context: |
  Monorepo with pnpm workspaces. Prefer minimal, targeted changes.

rules:
  proposal:
    - Include rollback plan
```

```yaml
# schema.yaml 中 proposal 的 instruction
instruction: |
  Create the proposal document. Focus on WHY, not HOW.
```

```markdown
<!-- templates/proposal.md -->
## Why
## What Changes
```

当一个 AI agent 生成 proposal 时，它实际收到的 prompt 大致是：

```text
<context>
Monorepo with pnpm workspaces. Prefer minimal, targeted changes.
</context>

<rules>
- Include rollback plan
</rules>

<instruction>
Create the proposal document. Focus on WHY, not HOW.
</instruction>

<template>
## Why
## What Changes
</template>

Please generate the proposal artifact based on the above.
```

---

## 决策表：什么时候改哪一层

| 你的诉求 | 改哪一层 |
|---------|---------|
| 所有 artifact 都需要知道的技术栈 | context |
| 只让 proposal 多写一个回滚计划 | rules.proposal |
| 想让 specs 强制用某种格式 | instruction (schema) |
| 想改变 proposal 的文档结构 | template |
| 想新增一个 artifact 类型 | schema（加 artifact + instruction + template） |
| 想删除 design 阶段 | schema（删 artifact + 改依赖） |

---

## 核心原则

> **context 给背景，rules 给约束，instruction 给方法，template 给形状。**

这四层合在一起，让你不需要写一行代码就能精确调控 AI 在每一个 artifact 阶段的行为。
