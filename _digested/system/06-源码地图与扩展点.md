# 源码地图与扩展点

## 读源码的入口顺序

建议不要从 `src/cli/index.ts` 一路线性读。更有效的顺序是：

1. 先看 `src/core/planning-home.ts`，明白 repo root 如何判定。
2. 再看 `src/commands/workflow/`，明白 agent runtime API。
3. 再看 `src/core/artifact-graph/`，明白 schema 如何变成状态图。
4. 再看 `src/core/init.ts`、`src/core/update.ts`，明白投递层。
5. 最后看 `src/core/store/` + `src/core/references.ts` + `src/core/root-selection.ts`，明白多仓库 store 模型。

## 常见扩展点

### 加一个新的 workflow

主要入口：

- `src/core/templates/workflows/<id>.ts`
- `src/core/profiles.ts`
- `src/core/shared/skill-generation.ts`

如果它需要新的 CLI runtime 数据，再看 `src/commands/workflow/`。

### 加一个新的 coding agent

主要入口：

- `AI_TOOLS` in `src/core/config.ts`
- `src/core/command-generation/adapters/`
- `src/core/command-generation/registry.ts`
- 相关 docs / digest

只支持 skills 的工具可以不提供 command adapter。

若新工具与既有工具共享同一 skills 根（当前 Codex、Zed 与 vendor-neutral `agents` 目标共享 `.agents`），还要接入 `src/core/shared-skill-target.ts` 的 ownership 机制——`.openspec-target` marker + `reconcileSharedSkillTargets()` 判定谁是当前 active writer，否则 `update` 不知道该让谁写这个共享根。

### 改 artifact completion detection

主要入口：

- `src/core/artifact-graph/outputs.ts`
- `src/core/artifact-graph/state.ts`

这会影响 `status`、`instructions`、propose/continue/apply 判断，风险高，测试要覆盖普通路径和 glob。

### 改 project config 注入

主要入口：

- `src/core/project-config.ts`
- `src/core/artifact-graph/instruction-loader.ts`
- `src/core/artifact-graph/resolver.ts`

要分清：`config.yaml` 是默认 schema + context/rules，不是 workflow 结构定义。

### 改多仓库/store 行为

主要入口：

- `src/core/planning-home.ts`
- `src/core/store/`
- `src/core/references.ts`
- `src/core/root-selection.ts`
- `src/core/working-set.ts`
- `src/commands/store.ts`、`src/commands/context.ts`

重点理解 store registry → reference 声明 → working set 组装的数据流，不要让 store 机制静默写入 referenced repo。

## 维护文档时的引用规则

为了减少行号漂移，这套 digest 后续优先引用：

- 函数名 + 当前大致路径
- 类名 + 当前大致路径
- schema 文件路径
- CLI 命令名和 JSON 字段名

只有在必须定位非常具体行为时，才引用行号。
