# 目录与状态边界

## 一句话

OpenSpec 的“状态”不是集中在一个配置文件里，而是按职责分散在几类目录里。判断某个文件重要不重要，先问它属于哪一层：项目事实、工作流定义、投递层、本机视图，还是团队协调上下文。

## repo-local 项目状态

```text
repo-root/
└── openspec/
    ├── specs/
    ├── changes/
    ├── config.yaml
    └── schemas/
```

| 路径 | 本质 | 是否是项目事实 |
|------|------|----------------|
| `openspec/specs/` | 当前 capability spec 基线 | 是 |
| `openspec/changes/<name>/` | 一次增量 change 工作区 | 是，直到 archive |
| `openspec/changes/<name>/.openspec.yaml` | 单次 change 的 schema 绑定等 metadata | 是 |
| `openspec/config.yaml` | 项目级默认 schema、context、rules | 是，但它是提示/默认层，不是 capability spec |
| `openspec/schemas/<name>/` | 项目本地 schema 定义 | 是，属于工作流定义 |

最容易想错的是 `config.yaml`。它不是项目能力清单，也不是 artifact DAG。它主要参与两件事：新建 change 时提供默认 schema；生成 instructions 时注入 context/rules。

## schema 与模板状态

schema 可以来自三类位置：

```text
repo-root/openspec/schemas/<name>/
getGlobalDataDir()/schemas/<name>/
package/schemas/<name>/
```

schema 目录的核心文件是：

```text
schema.yaml
templates/*.md
```

`schema.yaml` 定义 artifact id、输出路径、依赖关系、instruction、apply requires/tracks。template 是 artifact 输出内容的起始形状，不等于 schema 本身。

更细的字段和解析优先级见 `../schema/`，这里不展开。

## global config 与 global data

OpenSpec 有两个全局根：

| 根 | 来源函数 | 保存什么 |
|----|----------|----------|
| global config dir | `getGlobalConfigDir()` | `config.json`，profile/delivery/workflows 等用户级配置 |
| global data dir | `getGlobalDataDir()` | 用户级数据，例如 managed workspaces、context stores、用户级 schemas |

源码入口：

- `src/core/global-config.ts`
- `src/core/config-schema.ts`

global config 影响投递层：选择哪些 workflow，以及生成 skills、commands 还是两者都生成。它不保存某个 repo 的业务规格。

## agent 集成目录

不同工具有不同目录，例如 `.claude/`、`.cursor/`、`.cline/`、`.codex/` 等。OpenSpec 在这些目录里生成两类东西：

| 类型 | 本质 | 来源 |
|------|------|------|
| skill | agent 自动发现的能力说明书 | `getSkillTemplates()` + `generateSkillContent()` |
| command | slash/prompt 入口文件 | `getCommandContents()` + command adapter |

这些目录是投递层，不是项目事实。删除或重生成它们会影响 agent 能不能触发 workflow，但不会直接改变 `openspec/specs/` 或 `openspec/changes/` 的业务内容。

## workspace 本机视图

workspace 状态集中在 managed workspace root：

```text
getGlobalDataDir()/workspaces/<workspace-name>/
├── .openspec-workspace/
│   └── view.yaml
├── AGENTS.md
└── <workspace-name>.code-workspace
```

`view.yaml` 是本机私有视图记录，包含：

- workspace 名称
- selected initiative context
- linked repo/folder 名称到本机路径的映射
- preferred opener
- workspace skill 安装状态

workspace root 不是 owning repo。linked path 可以是 repo，也可以是普通文件夹。OpenSpec 不负责 clone、branch、sync 这些外部操作。

源码入口：

- `src/core/workspace/foundation.ts`
- `src/core/workspace/registry.ts`
- `src/core/workspace/state-io.ts`

## context store 与 initiative

context store 是更持久的协调上下文容器。它可以注册在 global data 下，也可以指向用户指定路径。

```text
<context-store-root>/
├── .openspec-store/
│   └── store.yaml
└── initiatives/
    └── <initiative-id>/
        ├── initiative.yaml
        ├── requirements.md
        ├── design.md
        ├── decisions.md
        ├── questions.md
        └── tasks.md
```

initiative 适合保存跨 repo 或跨团队的长期协调信息。workspace 可以打开某个 initiative，成为当前本机视图的上下文。

源码入口：

- `src/core/context-store/foundation.ts`
- `src/core/context-store/operations.ts`
- `src/core/collections/runtime.ts`
- `src/core/collections/initiatives/`

## 判断 source of truth 的经验法则

| 你看到的文件 | 应该怎么理解 |
|--------------|--------------|
| `openspec/specs/**/spec.md` | repo 当前 capability spec |
| `openspec/changes/<name>/**` | 某次 repo-local change 的计划和 delta |
| `.openspec-workspace/view.yaml` | 本机 workspace 视图，不是共享业务事实 |
| context store initiative 文件 | 可共享的协调上下文 |
| tool skills/commands | 给 agent 的入口和说明，可重生成 |
| generated `.code-workspace` | editor 打开视图，可重生成 |
