# 系统心智模型

## 先钉住主轴

OpenSpec 管的核心不是“AI 提示词”，而是：

```text
项目当前 spec 基线 + 针对这条基线的一次次增量 change
```

repo-local 形态下，这条主轴落在两个目录：

```text
repo-root/
└── openspec/
    ├── specs/                 ← 当前已经成立的 capability spec
    └── changes/<change>/      ← 一次准备中的增量 change
```

`specs/` 是项目当前被承认的行为合同。`changes/` 是某次改动的工作区，里面的 proposal、delta specs、design、tasks 说明这次准备怎么改。

这点比命令名称更底层。无论入口是 `/opsx:propose`、`openspec status`、还是 agent 读到某个 skill，最后都围绕这个状态模型运转。

## OpenSpec 不是什么

这几个边界很重要：

| 容易误解 | 更准确的说法 |
|----------|--------------|
| OpenSpec 是一个 LLM | OpenSpec 不做模型推理，创造性生成发生在宿主 coding agent 里 |
| OpenSpec 是一个 IDE 插件 | 它是 CLI + 文件状态 + 生成的 agent 指令 |
| skill/command 是项目事实 | skill/command 是投递层，项目事实在 `openspec/` 里 |
| schema 是模板别名 | schema 是 artifact DAG 和 apply 约束，template 只是其中一个字段引用 |
| store 是大一统 repo | store 是注册的 repo checkout；reference 只是索引引用，不合并 repo |

## 三方关系

```text
用户
  │
  │ 输入 /opsx:* 或自然语言请求
  ▼
宿主 coding agent
  │
  │ 读 OpenSpec 生成的 skill/command
  │ 调 openspec CLI 获取结构化状态
  │ 用自己的 LLM 推理并写文件
  ▼
OpenSpec CLI + 文件系统
  │
  │ status / instructions / archive / store / context ...
  ▼
repo-local openspec/ 或 store registry 状态
```

OpenSpec 的职责是给 agent 提供可验证的本地状态和执行包。agent 的职责是理解用户意图、调用 CLI、把 JSON 和文件内容交给模型推理、再执行实际写入或实现。

## repo-local change 的基本形状

默认 repo-local schema 是 `spec-driven`，典型 change 是：

```text
openspec/changes/add-dark-mode/
├── .openspec.yaml        ← 这次 change 绑定的 schema 元数据
├── proposal.md           ← 为什么改、改什么
├── specs/
│   └── ui/spec.md        ← 对主 specs 的 delta
├── design.md             ← 怎么改
└── tasks.md              ← 实施清单
```

这些文件不是长期主 spec。archive 之后，delta specs 会合并回 `openspec/specs/`，change 自身进入 archive 目录。

## 为什么 CLI 是 runtime API

agent 不应该靠猜目录来判断状态。当前源码把几个命令设计成 runtime API：

- `openspec status --json`：把 change 映射成 artifact 状态、apply gate、action context。
- `openspec instructions <artifact> --json`：把 template、instruction、context、rules、依赖内容编译成写作/执行包。
- `openspec new change`：创建一个带 metadata 的 change 实例。
- `openspec schemas/templates`：暴露可用 schema 和模板信息。

这就是 OpenSpec “本地协议层”的本质：文件系统保存状态，CLI 解释状态，agent 消费解释后的结构。

## store 模型进入后，心智模型怎么扩展（v1.5.0）

v1.5.0 用 store 模型替代了旧的 workspace/context-store/initiative。它不是替代 repo-local，而是加了一层上下文引用：

```text
全局 store registry（~/.openspec/stores/registry.yaml）
  └── 注册的 store（各自是独立 repo checkout）
       ├── .openspec-store/store.yaml     ← store 身份
       └── openspec/specs/                ← store 自身的 specs

项目 openspec/config.yaml
  └── references: [store-id, ...]         ← 声明"我还依赖这些 store 的 specs"

working set（openspec context 组装）
  └── root + referenced stores 的索引   ← agent 可消费的上下文摘要
```

store 帮 agent 看到其他仓库的 specs，但它只提供索引，不内联内容，不自动 merge，不替 referenced repo 决定业务归属。
