# 手段清单：到底有多少种修法

## 先回答标题：本质上只有 2 种原语

别背"七种手段"。把所有修法摊开看，真实结构是：

- **1 种修复原语**：用 delta 重新表达 + `archive`——就是 `01` 造 specs 的同一条流水线。
  - `/opsx:sync` 是它的 **LLM 变体**（跳过 rigid 合并、做整段重写）。
  - AUTHOR-NEW 是它的**加法情形**（delta 全是 ADDED，给已有代码补 spec）。
- **1 种清除原语**：文件操作（DELETE / SHELVE）——清掉不该进流水线的噪声 change。
- **1 个核选项**：手改主 spec + 再基线（流水线兜不住时；代价是失去可追踪性）。
- **2 个元实践**：前置纪律（防积累）、巡检（发现漂移）。

就这些。下面逐个讲清，最后给一张"信号 → 原语"速查。

> 主轴引用（`01`/`02`）：specs 只在 `archive` 更新、身份=标题、无工具持续对账 ⇒ 所以"修 specs"= 回到 archive 这条流水线重新表达，不是手搓 `spec.md`。下文命令都是 recipe，不替你执行。

## 修复原语：delta + `archive`（根本，对应旧"手段 1/2/4"）

**核心思想**：specs 是 delta 累加出来的，所以修 specs 也走 delta——写一个 change，用四操作把"想要的现状"表达出来，然后 `archive`。这覆盖了"改内容""删陈旧""补新能力"三件事。

**recipe**（archive 默认自校验，**不必单跑 `validate`**——见 `06`）：

```bash
openspec new change fix-<something>      # = propose，脚手架出 change
# 编辑 openspec/changes/fix-<something>/specs/<capability>/spec.md
openspec archive fix-<something> -y      # 自校验 + 把 delta 合进 spec + 收档
```

delta 该用哪个操作，按你想干什么选：

| 想干什么 | delta 操作 | 关键点 |
|----------|-----------|--------|
| 改大小写 / 改标题文字 | `RENAMED`（FROM/TO） | 配一个指向**新名**的 MODIFIED；别对旧名做 MODIFIED |
| 删掉陈旧 requirement | `REMOVED`（只要名字） | 名字必须和当前 spec **逐字一致**（仅 trim） |
| 改 requirement 内容 | `MODIFIED`（整块新版本） | **整块替换**，连同所有 scenario 写全；标题与现有一致 |
| 补新 requirement / 新 capability | `ADDED`（整块） | 同名已存在报 `already exists`；全 ADDED 即 AUTHOR-NEW |

**两个变体**：

- **AUTHOR-NEW（加法情形）**：delta 全是 `ADDED`，给已发运但无 spec 的 capability 补契约。**如实描述已发运行为**（读源码确认），不是写愿望；区分"该有 spec"和"本就不该有 spec"（内部引擎属 design/tasks，见 `02` 的 `profile-sync-drift`）。给**已有代码库**批量补 spec 的采用流程见 `08-给已有代码补spec-greenfield.md`。
- **host 的 sync workflow（LLM 变体）**：delta 太乱、或想整段重写一个 capability 时，让 agent 读 delta + 主 spec 做非确定再对齐（幂等）。它**不移动 change 到 archive**、只改 spec，跑完必须 `git diff` review。少量明确 → 直接 delta+archive（确定可审计）；大量混乱 → sync（灵活但要 review）。Codex 使用 `$openspec-sync-specs`，command adapter 的实际调用名以宿主为准。

**陷阱**：

- 精确名匹配 + 大小写敏感：`MODIFIED`/`REMOVED` 的名字要和主 spec 当前标题**逐字一致**；身份保留大小写，别假设会归一化。
- 原子性：一个 delta 块找不到目标，**整次 archive 回滚**（`Aborted. No files were changed.`），连能成功的部分也不落地。
- 新 capability 的 delta 应先写可用的 `## Purpose`；archive 会把它带入新 main spec。仅当 Purpose 缺失或无法构成可读内容时才得到 `TBD - ...` placeholder，仍应随后补真实 Purpose（<50 字会 WARNING）。

**可逆性**：specs 有 git 可回滚；change 进 archive 也能找回。

## 清除原语：DELETE / SHELVE 噪声 change（对应旧"手段 3"）

**核心思想**：① 悬空且不会建、④ 废弃但仍 active 的 change，本身就是噪声。`openspec` **没有删除/搁置 change 的 CLI 动词**，所以是文件操作。

```bash
# 设计还有价值、只是暂时不建 → 搁置（可逆，推荐）
mkdir -p openspec/explorations && mv openspec/changes/<shelved-change> openspec/explorations/
# 死透 / 重复 / 明显错方向 → 删（不可逆，慎用）
rm -rf openspec/changes/<dead-change>
```

判断：有可观 design/proposal → SHELVE；纯空壳/重复/错方向 → DELETE；**拿不准一律 SHELVE**（可逆优先）。陷阱：DELETE 不可逆；别清一个别人正在做的 change（先看 `tasks.md` 和改动时间）；搁置前确认没被 initiative/别的 change 引用为前置。

## 核选项：手改主 spec + 再基线（对应旧"手段 5"）

**只在流水线兜不住时用**：spec 漂得没有任何 delta 能干净表达修正（整段面目全非）。直接编辑 `openspec/specs/<cap>/spec.md`，再写一个 rebaseline change 把新基线登记进档案。

```bash
$EDITOR openspec/specs/<capability>/spec.md          # 1. 手改
openspec new change rebaseline-<capability>          # 2. 登记
# 写 delta（ADDED/MODIFIED）反映新基线
openspec archive rebaseline-<capability> -y
```

**最该警惕**：没有任何工具追踪你手改过。手改后历史 delta 和新标题必然对不上，后续指向旧标题的 delta 全 `not found`。所以手改**必须**配 rebaseline change 登记新标题体系，否则只是把今天的失真换成明天的。**优先穷尽修复原语后再用这一招。**

## 元实践一：前置纪律（防积累，对应旧"手段 6"）

失真能积累，是因为流程上有缝；堵缝比事后修便宜。

| 纪律 | 防住哪类噪声 |
|------|-------------|
| change 做完**立刻 archive**，别长期挂 active | ① ④ |
| 改名**走 RENAMED**，绝不"删旧的 + 加新的" | ⑥ |
| capability path **保持稳定**——**capability 没有 RENAMED 操作**（requirement 才有），改 path 是裸搬目录、必须同步所有引用它的 delta | ① ⑥ |
| `openspec validate --all --strict` 当 **CI 结构闸**（只挡结构坏死，不挡漂移） | ④（结构性） |
| 新 capability delta 中**先写 Purpose**、定期 review spec vs 代码 | ③ |
| 手改 spec 只作最后手段，且必配 rebaseline change | ⑥ |

纪律是人的行为，没工具强制；团队要有人守，否则慢慢回到默认失真。

## 元实践二：巡检（发现漂移，对应旧"手段 7"）

工具不提供全局一致性巡检（见 `06`），所以"specs 还对不对得上"要靠人定期巡检。（用**巡检**不用"审计"——后者暗示一个 `06` 已说**不存在**的自动化工具。）

一套可重复手法：

1. **盘点**：`openspec list --specs` / `openspec list` / `openspec view`。
2. **抓结构性坏死**：`openspec validate --all`（任何 ✗ 多半是 ④ 无 delta 且未声明 `skip_specs: true` 的僵尸 change——只这一类它抓得到）。
3. **抓悬空 delta 目标（①）**——无命令，grep：
   ```bash
   find openspec/changes -path '*/specs/*/spec.md' -type f -print | while read -r spec; do
     rel=${spec#*/specs/}
     rel=${rel%/spec.md}
     [ -f "openspec/specs/$rel/spec.md" ] || echo "DANGLING: $spec → specs/$rel/spec.md 不存在"
   done
   ```
4. **抓有代码无 spec（②）**：`src/commands/` 的能力对照 `openspec/specs/`（人工判断哪些该有 spec）。
5. **抓冻结 spec（③）**：挑关键 spec，把声明的行为和当前代码对一遍（或 host 的 verify workflow 辅助）。
6. **重建溯源**（"这条 requirement 当年为什么进来"）：`grep -rn "### Requirement: <Name>" openspec/changes/archive/`。

巡检只读、不改；产出一份"漂移清单"直接喂给上面的原语去修。

## 信号 → 原语 速查

| 噪声信号（详见 `02`） | 用哪个原语 |
|----------------------|-----------|
| ① 悬空 delta 目标 | 清除（DELETE/SHELVE）或 修复（AUTHOR-NEW） |
| ② 有代码无 spec | 修复（AUTHOR-NEW，见 `08` greenfield） |
| ③ 冻结 spec | 修复（纠正型 delta）或 核选项（再基线） |
| ④ 废弃仍 active change | 清除（DELETE/SHELVE） |
| ⑤ 平行权威层未对齐 | 修复（更新 conventions spec；详见 `09`） |
| ⑥ 身份脆弱性（ur-cause） | 修复（RENAMED）或 核选项（再基线） |
| 想预防 / 想发现 | 元实践（纪律 / 巡检） |

```text
specs 和现实对不上
   ├── 内容要变（③⑤⑥） → 少量明确: 修复原语(delta+archive) / 大量混乱: /opsx:sync 或 核选项(再基线)
   ├── 漏了能力（②）    → 修复原语(AUTHOR-NEW)
   ├── 噪声 change（①④）→ 清除原语(DELETE/SHELVE)
   └── 想预防/想发现    → 元实践(纪律/巡检)
```

## 守住的边界

所有修法都围绕一个立场：**specs 是事实层，修它要回到 archive 这条受控流水线，不是随手编辑。** 修复原语走流水线；清除原语清掉不该进流水线的噪声；核选项是流水线兜不住时的代价（失可追踪性）；两个元实践保证流水线长期不淤。把"别手搓 spec"当默认，就守住了 source of truth 的边界。
