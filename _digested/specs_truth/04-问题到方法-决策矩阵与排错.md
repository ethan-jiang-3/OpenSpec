# 问题到方法：决策矩阵与排错

## 一句话

把 `02` 的噪声信号和 `03` 的原语接起来：看到一个症状，怎么诊断、用哪个原语、跑什么命令。重点给一棵 `archive ... not found` 诊断树（本 repo 真实案例），再加跨 change 冲突怎么处理。

## 决策矩阵：症状 → 诊断 → 原语 → 命令

| 症状 | 诊断 | 原语（见 `03`） | 命令 / 动作 |
|------|------|----------------|-------------|
| `archive` 报 `MODIFIED failed ... not found` | delta 指向的标题在当前主 spec 已不存在（改名/重写/手改） | 修复 / 核选项 | 先 grep 当前标题；能对上就改 delta 名字 → archive；对不上就再基线 |
| archive 输出 REMOVED 已不存在 warning | 删除已被 early-sync 完成 | 无 | 可直接继续 archive；若主 spec 有大小写/空白近似名，改 delta 精确匹配而不是把 warning 当成功 |
| `archive` 报 `RENAMED failed ... source not found` | 旧名对不上；若 TO 已存在且 FROM 真不存在，则是 early-sync no-op | 修复 / 无 | 先核对 TO 是否已存在；只有两端都不对时才改 FROM 名字 |
| `archive` 报 `RENAMED failed ... target already exists` | TO 名字已存在 | 修复 | 换 TO 名，或先 REMOVED 冲突项 |
| `archive` 报 `ADDED failed ... already exists` | 要加的已存在且内容不同 | 修复 | 完全相同是 early-sync no-op；不同则改用 MODIFIED 或确认冲突 |
| `validate --all` 一堆 `✗ ... No deltas found` | 僵尸 change：只有 proposal、没 `specs/` delta，且未声明 `skip_specs: true`（④） | 清除 | SHELVE 到 `explorations/` 或 DELETE；纯非行为工作可声明 marker |
| spec 说"有"、代码早没了（③） | 冻结 spec | 修复 / 核选项 | 纠正型 delta（REMOVED/MODIFIED）→ archive |
| 代码有、spec 没说（②） | 漏报现状 | 修复（AUTHOR-NEW） | AUTHOR-NEW capability spec → archive |
| active change 长期 archive 不掉 | 多为 ① 悬空目标 或 ⑥ 标题失配 | 清除 / 修复 / 核选项 | 见下面诊断树 |
| conventions/结构 spec 过时（⑤） | 新层没被承认 | 修复 | MODIFIED conventions spec → archive（详见 `09`） |
| `## Purpose` 是 `TBD - created by archiving...` | 新 capability delta 未提供可用 Purpose，archive 才使用 fallback | （补 Purpose） | 直接补 main spec；之后创建新 capability 时把 Purpose 写在 delta（<50 字 WARNING） |
| 两个 open change 撞同一个 requirement | 跨 change 冲突（见下节） | 修复 | 按依赖顺序 archive / 合并成一个 change |
| archive 报空 spec 且列出 blocking lines | 最后一个 requirement 已移除，但 `## Notes`、orphan prose/注释会随整文件删除 | 内容治理 / 退役 | 先迁入 Purpose 或 canonical requirement，或人工删除；此时加 `retire_capabilities` 也无效 |

## 重点排错：`archive ... not found` 诊断树

最高频、最让人懵的一类。典型报错（本 repo 真实抓到，完整诊断只在这一处）：

```text
Specs to update:
  cli-init: update
  cli-update: update
  profiles: create
  propose-workflow: create
cli-init MODIFIED failed for header "### Requirement: Skill generation per tool (REPLACES fixed 9-skill mandate)" - not found
Aborted. No files were changed.
```

报错只给一行 `... - not found`，**不告诉你当前 spec 里实际有哪些名字**。诊断自己来：

```text
看到 "X failed for header "### Requirement: <Name>" - not found"
   │
   1. 先从 status/instructions JSON 读取 planningHome.root
      再看 <planningHome.root>/openspec/specs/<capability>/spec.md 有哪些 requirement
      （repo-local 项目中 planningHome.root 才通常等于当前仓库根）
   │
   2. 对照 delta 里的 <Name>，判断属于哪种：
   ├── (a) 只是大小写/标点不同 → 身份保留大小写、无归一化
   │      → 修复原语：RENAMED（FROM 旧→TO 新）扳正，或把 delta <Name> 改成逐字一致
   ├── (b) 完全不同（被别的 archive 重写过，如本例）→ delta 停旧标题、spec 已演化
   │      → 映射清晰：修复原语，逐条改 delta 名字对齐
   │      → 映射混乱/整段面目全非：核选项，手改 spec 再基线
   ├── (c) 目标早该不存在了 → 修复原语：从 delta 删掉这条
   └── (d) delta 指向从没存在过的名字（笔误/臆造）→ 修复原语：改正 delta 名字
   │
   3. 改完 archive（archive 自校验，不必单跑 validate）
      openspec archive <change> -y
   │
   4. 记住原子性：一次 not found 让整批（含本来能成功的）都不落地
      → "能成功的部分"等失败项修完一起 archive
```

**本例（`simplify-skill-installation`）落在分支 (b)**：16 条目标全对不上——不是大小写，是 spec 之后被别的 archive 整体重写过。可选：核选项（手改 `cli-init`/`cli-update` 对齐代码 + rebaseline 登记）；或清除 + 修复（把过时 change SHELVE，为 `profiles`/`propose-workflow` 从当前代码 AUTHOR-NEW）。代码已是既成事实时，后者更干净。

## 空 spec + blocking lines

这不是普通的 “缺 marker”：

```text
removes last requirement
  ├─ 无 unaccounted content、只缺授权 → 添加 retire_capabilities: true
  ├─ 有 blocking lines → 先清理/迁移内容；marker 不是出路
  └─ marker 已存在仍失败 → 修 invalid marker/schema，或清理输出点名的内容
```

输出会安全截取最多 3 行、每行 200 code points，并清理控制字符。不要用 `--no-validate` 或反复加 marker 绕过，因为保护的是整文件删除造成的真实信息丢失。

## 跨 change 冲突：两个 open change 撞同一个 requirement

`validate` 逐个 change 校验、**不比较 change 之间**（见 `02`/`06`），所以两个 open change 都改同一个 requirement 时，各自都过 validate。冲突只在 archive 时暴露：

- change A **RENAMED** `Login`→`SignIn` 并先 archive ⇒ `Login` 没了；
- change B（仍 open，写于 A archive 前）**MODIFIED** `Login` ⇒ B archive 时 `Login` not found，整批回滚。

**怎么发现**：巡检时看是否有多个 open change 的 delta 指向同一 capability 的同名 requirement（grep 各 change 的 `specs/`）。

**怎么修**：
- **按依赖顺序 archive**：先归档 RENAMED/REMOVED 的那个，再把后续 change 的 delta 名字更新到新名后归档；
- 或**合并成一个 change**：把两处改动并进同一个 change 的 delta，一次 archive（避免顺序依赖）。

## 修复原语 recipe 模板（参数化）

纠正/改名/删/补都是同一个模板，只换段头和块内容（archive 自校验，不必单跑 validate）：

```bash
openspec new change <change-name>          # = propose
# 编辑 openspec/changes/<change-name>/specs/<capability-path>/spec.md，按需选段头：
#   ## REMOVED Requirements   → ### Requirement: <Exact Current Name>      （删；先 grep 确认名字）
#   ## RENAMED Requirements   → FROM: `### Requirement: Old` / TO: `### Requirement: New`  （改名；别用"删旧+加新"）
#   ## MODIFIED Requirements  → 整块新版本（标题与现有一致）                 （改内容）
#   ## ADDED Requirements     → 整块（带 SHALL/MUST + ≥1 Scenario）          （补；= AUTHOR-NEW）
openspec archive <change-name> -y          # 自校验 + 合并 + 收档；新 capability 的 delta 应自带 ## Purpose
```

**清除原语**（僵尸 change，单独一套，因为是文件操作）：

```bash
openspec validate --all            # 确认哪些 ✗（多是无 delta 的僵尸 change）
mkdir -p openspec/explorations
mv openspec/changes/<zombie> openspec/explorations/   # 优先 SHELVE；死透才 rm -rf
openspec validate --all            # 复查：那几个 ✗ 应清零（只证明僵尸清了，不证明 specs 对齐）
```

## 守住的边界

排错核心：**`not found` 不是 bug，是身份模型在告诉你"delta 和 spec 漂移了"。** 别急着 `--no-validate` 强行 archive（那会把漂移焊死进真相）。正确反应永远是先查当前 spec 的实际标题，再决定修 delta（修复原语）还是再基线（核选项）。
