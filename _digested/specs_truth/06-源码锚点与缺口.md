## validate 命令参考

`openspec validate` 是 **CLI 命令**（和 `archive` 同列），**不是 `/opsx:` slash 技能**（没有 `/opsx:validate`）。它是**结构 linter**——本专题里关于 validate 的一切边界都源于此。

**它查什么**（机理见 `02` 缺口一）：
- 主 spec：结构（Zod：Purpose/Requirements 非空、每条 requirement **至少一个 scenario**——缺了是 ERROR；`findMainSpecStructureIssues`：无残留 delta 段头、无越界 requirement）；SHALL/MUST 是 **guidance 而非硬错误**：正文整体缺失才 ERROR，正文在但缺 SHALL/MUST 仅 WARNING（`applySpecRules` 逐块检查，不再走 Zod refine）；Purpose <50 字 WARNING、requirement >500 字 INFO。
- change delta：段头齐全；SHALL/MUST 同样放宽为 guidance（normal 模式正文缺关键字仅 WARNING，**strict 模式**才把 WARNING 当失败；正文整体缺失仍是 ERROR）；ADDED/MODIFIED 缺 scenario 仍是 ERROR；段内重名、跨段冲突；根级 `specs/spec.md` 会报错；**整个 change 没 delta → `CHANGE_NO_DELTAS` ERROR，除非 `.openspec.yaml` 显式 `skip_specs: true`**（抓僵尸 change，而不逼纯重构/工具/文档 change 虚构 requirement）。marker 与 specs 下任意非隐藏文件共存也报错。

**它查不出什么**（不跨文件对账）：delta 目标不存在、ADDED 与主 spec 重复、跨 change 冲突、specs↔代码漂移——这些仍静默过。唯一例外：`validate <change>` 能拿到主 spec（`mainSpecsDir`）时，会对 **MODIFIED 块做 scenario-loss 前置检测**——若省略了主 spec 仍保留的 scenario，直接报 ERROR 并指名要抄回的 scenarios（archive 本来就会拒绝这种 loss，现在 authoring 阶段就拦下）。这个计数与主 spec 路径对齐：requirement 下**每一个非 fence 的 `#### ` 子标题**都算 scenario（不只是字面 `#### Scenario:`；`#### Edge case` 也算）。比较时剥可选 `Scenario:` 前缀。`--archived` 检查的是 archive 里 tasks 勾选，仍然不是 specs↔代码对账。

**选项**：

| 选项 | 作用 |
|------|------|
| `--all` | 校验所有 changes + specs（项目外失败，不 silent pass） |
| `--changes` / `--specs` | 只校验一类（同样要求已有 OpenSpec root） |
| `--archived` | opt-in，检查 `changes/archive/` 每个 change 的 tasks 是否全部勾完；独立 scope，不重验 delta |
| `--type change\|spec` | 单个名字歧义时消歧 |
| `--strict` | WARNING 也算失败（INFO 永不算） |
| `--json` | 输出 `{ items, summary, version: '1.0' }` |
| `--concurrency <n>` | 并发，默认 env `OPENSPEC_CONCURRENCY` 或 6 |
| `--no-interactive` | 关交互 |

退出码：单条 `valid ? 0 : 1`；批量 `failed > 0 ? 1 : 0`。`--strict`/`--json`/`--concurrency` 是为 CI 设计的——`validate --all --strict --json` 当 **CI 结构闸**是它的本来用途（**只挡结构坏死，不挡漂移**）。

**与 archive 的关系（为什么 archive 前不必单跑 validate）**：`archive` 默认自校验（`--no-validate` 可跳），调 `validateChange`（proposal，非阻塞）+ `validateChangeDeltaSpecs`（delta，阻塞——和单跑 validate 同一个方法）+ 合并后 `validateSpecContent`（阻塞）。单跑 validate 抓的 archive 都抓，archive 还多查合并结果——**archive 前单跑 validate 是冗余**。

**何时真用得上**：CI 结构闸；偶尔手动体检抓僵尸/结构烂。帮不上：挡不住 specs↔代码漂移（那靠巡检/对账，见 `03`/`05`）。

## 诚实声明：OpenSpec 不提供的能力

这是专题里反复出现、必须挑明的边界。下面这些能力**都不存在**（已用 grep / 命令注册表核验）：

| 你可能想要的能力 | 现实 | 怎么办（workaround，见 `03`） |
|------------------|------|-------------------------------|
| **回溯 / 溯源**：`openspec log`/`blame`/`history`/`trace`，问"这条 requirement 当年为什么进来" | 不存在。归档 change 只被原样搬到 `changes/archive/`，无反向索引 | 巡检：`grep -rn "### Requirement: <Name>" openspec/changes/archive/` 人肉重建溯源 |
| **修复 / 再生成**：`openspec reconcile`/`repair`/`regenerate` | 不存在（`/opsx:sync` 是 LLM skill，非确定命令） | 修复原语（delta+archive）或核选项（再基线） |
| **裁剪 / 清理**：`openspec prune`/`clean` | 不存在 | 清除原语（文件操作 DELETE/SHELVE） |
| **`apply` 命令**：不归档、只把 delta 应用到 spec | 不存在（`applySpecs` 是 archive 内部引擎，无独立 CLI） | 用 `archive`；想跳过 rigid 合并用 `/opsx:sync` |
| **全局一致性审计**：扫出孤儿 spec、悬空 delta、code↔spec 漂移 | 不存在 | 巡检（元实践，含本文 grep/脚本） |
| **手改检测**：发现有人直接编辑过主 spec | 不存在（无 hash/checksum 对账） | 前置纪律（别手改；改了必配再基线） |
| **稳定 requirement ID** | 不存在（身份 = 标题文本） | 前置纪律（改名走 RENAMED；标题当稳定契约） |
| **capability rename** | 不存在（身份 = `specs/` 下相对 path；改 path 只能搬目录，旧 delta 会失配） | 前置纪律（capability path 当稳定性契约，能不改就不改） |
| **validate 跨文件对账**：delta 目标是否真在主 spec 里 | 不做（`validateChangeDeltaSpecs` 不读主 spec） | archive 时以 `not found` 暴露；排错见 `04` |

一句话总结这条边界：

> **OpenSpec 用 `archive` 把"写 specs"这一刻管得很可靠；但 specs 一旦写下去，就再没有任何工具持续盯着它对不对。** 回溯、修复、裁剪、审计——全是空位。所以 specs 的长期质量 = 前置纪律 + 定期巡检，不是某个命令的责任。（为什么 OpenSpec 故意不给 reconcile，见 `02` 开篇的设计视角。）
