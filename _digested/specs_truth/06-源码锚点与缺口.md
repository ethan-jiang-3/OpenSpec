## validate 命令参考

`openspec validate` 是 **CLI 命令**（和 `archive` 同列），**不是 `openspec-*` 技能**（没有 `openspec-validate`）。它是**结构 linter**——本专题里关于 validate 的一切边界都源于此。

**它查什么**（机理见 `02` 缺口一）：
- **项目配置可读性（#2127，`validate.ts:123-141`）**：执行任何单项或批量校验前，先通过 `readConfigParseError(root.path)` 检查 `openspec/config.yaml`（或 `.yml`）；若不可读或 YAML 语法损坏，直接报 `unreadable_config` / `unparseable_config` 并以退出码 **1** 退出（其他命令对此仅打 warning 回退默认值，由 `validate` 承担 CI 守门）。
- 主 spec：结构（Zod：Purpose/Requirements 非空、每条 requirement **至少一个 scenario**——缺了是 ERROR；`findMainSpecStructureIssues`：无残留 delta 段头、无越界 requirement）；SHALL/MUST 是 **guidance 而非硬错误**：正文整体缺失才 ERROR，正文在但缺 SHALL/MUST 仅 WARNING（`applySpecRules` 逐块检查，不再走 Zod refine）；scenario 缺少 `WHEN`/`GIVEN` + `THEN` 条目报 **WARNING**（#2079）；Purpose <50 字 WARNING、requirement >500 字 **WARNING**（v1.14.1 起，此前是 INFO）。
- change delta：段头齐全；**未识别的 `## ... Requirements` 段头**（如 `## UPDATED Requirements`，#2207）下若含 requirement 直接报 **ERROR**（`archive` 同样拒绝）；SHALL/MUST 同样为 guidance（normal 模式正文缺关键字仅 WARNING，**strict 模式**把 WARNING 当失败；正文整体缺失仍是 ERROR）；ADDED/MODIFIED 缺 scenario 仍是 ERROR；scenario 缺 `WHEN`/`GIVEN` + `THEN` 报 **WARNING**（#2079）；**ADDED 的正文 >500 字报 WARNING**，且 v2.1.1（#2265，`validator.ts:789-801`）起 **MODIFIED 正文满足 `nextText.length > 500 && nextText.length > currentTextLength`**（即正文总长度超过 500 字符，且比主 spec 里的基线更长——哪怕只多 1 个字符）也报 **WARNING**（虽超 500 字符但持平或缩短则不报警）；段内重名、跨段冲突；根级 `specs/spec.md` 报错；**整个 change 没 delta → `CHANGE_NO_DELTAS` ERROR，除非 `.openspec.yaml` 显式 `skip_specs: true`**（marker 与 `specs/` 下任意非隐藏文件共存也报错）。
- **delta 里"归档不会带走"的文本**（v1.14.2 #2054 WARNING；v2.1.1 #2273 豁免顶部 YAML frontmatter）：`parseDeltaSpec` 返回 `unappliedContent`，`validate` 把它报成 WARNING、`archive` 在 `buildUpdatedSpec` 时 `warn()`。三处边界：第一个 `## ` 之前的正文；`## ADDED/MODIFIED Requirements` 里第一个 requirement 之前的散文；除 Purpose 与四类 delta 段之外的任何 `## ` 段（如 `## Notes`）。与其他警告一致——正常通过，`--strict` 失败。**v2.1.1（#2273）起，文件顶部合法的 YAML frontmatter 不计入 `unappliedContent`**（`validate --strict` 通过，`archive` 仅打印一条说明该 frontmatter 不会带入主 spec 的提示）；HTML 注释、`# ` 标题、Purpose 段、REMOVED/RENAMED 正文都不告警。

**它查不出什么**（不以退出码拦截跨文件语义漂移）：跨 change 冲突、specs↔代码漂移完全不查。对于当前 change 与主 spec 的关系，`openspec validate <change>` 传入 `mainSpecsDir` 时只做两件事：
1. **MODIFIED scenario-loss 硬拦截（ERROR，退出码 1）**：若 MODIFIED 省略了主 spec 仍保留的 scenario，直接报 ERROR 并指名要抄回的 scenarios（计数认 requirement 下每一个非 fence 的 `#### ` 子标题，比较时剥可选 `Scenario:` 前缀）；
2. **合并冲突预演 `findArchiveBlockers`（`validator.ts:1000-1055`，仅报 INFO，退出码恒为 0）**：干跑 `buildUpdatedSpec`——当 `MODIFIED` 找不到目标、`RENAMED` 的 `FROM` 与 `TO` 都不存在（或有近似名）、`ADDED` 与主 spec 内容不同但重名时，输出 `INFO: Archive would refuse this delta: ...`，**即使加 `--strict` 也不会让退出码变 1**；而 `REMOVED` 指向早已不存在的 requirement 在无近似名时连 INFO 都不产生（按 early-sync no-op 放过）。`--archived` 检查的是 `changes/archive/` 里 tasks 勾选，同样不是 specs↔代码对账。

**选项**：

| 选项 | 作用 |
|------|------|
| `--all` | 校验所有 changes + specs（项目外失败，不 silent pass） |
| `--changes` / `--specs` | 只校验一类（同样要求已有 OpenSpec root） |
| `--archived` | opt-in，检查 `changes/archive/` 每个 change 的 tasks 是否全部勾完；独立 scope，不重验 delta |
| `--report <full\|findings>` | 仅配合批量范围（`--all` / `--changes` / `--specs` / `--archived`，不可与单项名同用，不可混用 archived 与 active）：`findings` 只返回存在 issues 的条目及统计摘要 |
| `--type change\|spec` | 单个名字歧义时消歧 |
| `--strict` | WARNING 也算失败（INFO 永不算）；「主 spec / ADDED 正文 >500 字」「MODIFIED 正文 >500 字且超过主 spec 基线（#2265）」「Scenario 缺 WHEN/GIVEN+THEN（#2079）」「delta 里的 unapplied 文本（不含合法顶部 YAML frontmatter，#2273）」都会让它失败 |
| `--json` | 输出 JSON 报告（单项或批量 `{ items, summary, root }`；`--report findings` 返回 `validation-findings` 投影） |
| `--concurrency <n>` | 并发，默认 env `OPENSPEC_CONCURRENCY` 或 6 |
| `--no-interactive` | 关交互 |
| `--store <id>` / `--store-path <path>` | 针对外部 planning store 根目录执行校验 |

退出码：单条 `valid ? 0 : 1`；批量 `failed > 0 ? 1 : 0`。`--strict`/`--json`/`--concurrency` 是为 CI 设计的——`validate --all --strict --json` 当 **CI 结构闸**是它的本来用途（**只挡结构坏死，不挡漂移**）。

**与 archive 的关系（为什么 archive 前不必单跑 validate）**：`archive` 默认自校验（`--no-validate` 可跳），调 `validateChange`（proposal，非阻塞）+ `validateChangeDeltaSpecs`（delta，阻塞——和单跑 validate 同一个方法）+ 合并后 `validateSpecContent`（阻塞）。单跑 validate 抓的 archive 都抓，archive 还多查合并结果——**archive 前单跑 validate 是冗余**。

**何时真用得上**：CI 结构闸；偶尔手动体检抓僵尸/结构烂。帮不上：挡不住 specs↔代码漂移（那靠巡检/对账，见 `03`/`05`）。

## 诚实声明：OpenSpec 不提供的能力

这是专题里反复出现、必须挑明的边界。下面这些能力**都不存在**（已用 grep / 命令注册表核验）：

| 你可能想要的能力 | 现实 | 怎么办（workaround，见 `03`） |
|------------------|------|-------------------------------|
| **回溯 / 溯源**：`openspec log`/`blame`/`history`/`trace`，问"这条 requirement 当年为什么进来" | 不存在。归档 change 只被原样搬到 `changes/archive/`，无反向索引 | 巡检：`grep -rn "### Requirement: <Name>" openspec/changes/archive/` 人肉重建溯源 |
| **修复 / 再生成**：`openspec reconcile`/`repair`/`regenerate` | 不存在（`/openspec-sync-specs` 是 LLM skill，非确定命令） | 修复原语（delta+archive）或核选项（再基线） |
| **裁剪 / 清理**：`openspec prune`/`clean` | 不存在 | 清除原语（文件操作 DELETE/SHELVE） |
| **`apply` 命令**：不归档、只把 delta 应用到 spec | 不存在（delta→主 spec 的合并是 `specs-apply.ts` 的内部能力，由 archive 调用，无独立 CLI） | 用 `archive`；想跳过 rigid 合并用 `/openspec-sync-specs` |
| **全局一致性审计**：扫出孤儿 spec、悬空 delta、code↔spec 漂移 | 不存在 | 巡检（元实践，含本文 grep/脚本） |
| **手改检测**：发现有人直接编辑过主 spec | 不存在（无 hash/checksum 对账） | 前置纪律（别手改；改了必配再基线） |
| **稳定 requirement ID** | 不存在（身份 = 标题文本） | 前置纪律（改名走 RENAMED；标题当稳定契约） |
| **capability rename** | 不存在（身份 = `specs/` 下相对 path；改 path 只能搬目录，旧 delta 会失配） | 前置纪律（capability path 当稳定性契约，能不改就不改） |
| **validate 跨文件硬拦截**：delta 目标是否真在主 spec 里 | 不以失败退出码拦截（仅 MODIFIED 丢 scenario 报 ERROR；`MODIFIED` 缺目标、`RENAMED` 两端皆缺或 `ADDED` 异内容重名只经 `findArchiveBlockers` 报 INFO、退出码仍为 0；`REMOVED` 已不在主 spec 时无告警） | archive 时以 `not found` 硬拒绝；排错见 `04` |

一句话总结这条边界：

> **OpenSpec 用 `archive` 把"写 specs"这一刻管得很可靠；但 specs 一旦写下去，就再没有任何工具持续盯着它对不对。** 回溯、修复、裁剪、审计——全是空位。所以 specs 的长期质量 = 前置纪律 + 定期巡检，不是某个命令的责任。（为什么 OpenSpec 故意不给 reconcile，见 `02` 开篇的设计视角。）

## spec 文件可以是项目内的 symlink（v1.14.2/v1.14.3）

`openspec/specs/<capability-path>/spec.md` 允许是指向**项目内**任意位置的相对 symlink——典型场景是 spec 文件住在产品文档旁边。规则收在新模块 `src/utils/spec-path-containment.ts`：

| 函数 | 语义 |
|---|---|
| `assertSpecFileWithin(root, file)` | spec 文件的字面包含检查，允许"叶子是链接" |
| `assertDiscoveredSpecFile(specsRoot, file)` | discovery 场景：字面检查失败后，只有当能力目录**本身仍在 specs root 内**（词法判断）才把能力目录当作文件自己的信任根——一个在路径解析后被换成链接的能力目录会被拒绝，而不是重新信任 |

配套的两个关键约束：

- **`findProjectRoot()`**：从 specs root 向上找 `<X>/openspec`，且其下层必须是 `specs` 或 `changes`，两条同时成立才算规划根，**父目录**才是项目边界。这个限定是必需的——否则放在 `~/openspec/my-store` 的 store 会把 `~` 当边界。经由其他途径到达的 specs root（如按路径给出的 store）没有可命名的项目，包含检查停在 specs root。悬空链接报错。
- **写侧钉定**（`writeUpdatedSpec`）：写入前把已验证的 `update.target` 经 `canonicalizeExistingPath` 钉住，`beforeMutate` 之后**再查一遍**，canonical path 变化就拒绝（`Spec target for '<id>' changed before it could be written`）。检查后被重新指向的链接不能把写入导到未校验的文件。

`archive` 侧的口径略有不同：`openspec/`、`changes/` 与 `specs/` **本身**可以是 symlink（走 `assertPathWithinAllowingLinkedLeaf`：只限制**父目录**在允许范围内，解析后的**叶子目标可以在任何已存在路径**，指向共享/外部文档仓库正是它的用途；悬空链接报错）。`archive/` 不同——它必须留在所在 changes 目录内，不允许是链接。

## `.openspec.yaml` 的 7 个已知顶层键与 `x-` 扩展键（v1.14.2）

`.openspec.yaml` 的官方顶层已知键共 **7 个**（`CHANGE_METADATA_KNOWN_KEYS`，定义在 `src/core/change-metadata/schema.ts:24-32`）：
- `schema`、`created`、`goal`、`affected_areas`、`initiative`、`skip_specs`、`retire_capabilities`

除上述 7 个已知键外，顶层以小写 `x-` 开头的扩展键属于使用者或外部工具：OpenSpec 不读、不写、不校验、不报未知。判定常量是 `EXTENSION_KEY_PATTERN = /^x-\S+$/`（`src/utils/change-metadata.ts:26`）。任何既不在 7 个已知键中、也不匹配 `/^x-\S+$/` 的顶层键（如拼错的 `skip_design` 或大写 `X-Tracker`）都会被 `readUnknownChangeMetadataKeys` 作为 **WARNING** 报出。

实测（v1.14.3）：`.openspec.yaml` 里放 `x-tracker: {...}` 时 `validate <change> --strict` **exit 0**；改成 `X-Tracker: {...}` 会出 WARNING，而 WARNING 会让 `--strict` **exit 1**。所以"扩展键不挡 strict"只对**合法的小写 `x-` 键**成立。另外这跟 delta 是两件事——没有 delta 的 change 即使扩展键合法，仍要 `skip_specs: true` 才不报 `Change must have at least one delta.`

| 规则 | 说明 |
|---|---|
| 前缀 | 必须小写 `x-`；`X-Tracker` 仍以 **WARNING** 报未知——而 WARNING 会让 `validate --strict` 失败 |
| 名字 | 前缀后至少一个字符、无任何空白；`x-jiraKey`、`x-trackerID` 都合法，裸 `x-` 与 `x- tracker` 不合法 |
| 值 | 任意 YAML，OpenSpec 不解释 |
| 作用域 | **仅顶层**；`initiative:` 内部仍是严格 schema，任何额外键都拒绝 |

一个容易踩的坑：`ChangeMetadataSchema` 会 strip 未知键（**包括 `x-*`**），所以任何重写既有 `.openspec.yaml` 的调用方必须先从原始 YAML 把扩展键合并回来，否则会静默删掉它们。

## 已知的 spec-vs-code 漂移（v1.14.3 同步时发现，上游尚未修）

`openspec/specs/cli-archive/spec.md` 的 Scenario `User declines confirmation` 写的是：

> **THEN** abort the entire archive operation
> **AND** display message: "Archive cancelled. No changes were made."
> **AND** exit with non-zero status code

但 v1.14.x 的 `archive` 实际行为（源码 + 实测一致）是：用户对 `Proceed with spec updates?` 答 `n` 后打印 `Skipping spec updates. Proceeding with archive.`，**照常归档并 exit 0**——因为拒绝的只是"更新主 specs"这一步，change 目录依然要移进 `archive/`。

这是"spec 落后于代码"的一个活样本，恰好印证本篇的立论（工具不做 code↔spec 对账）。**读文档时以代码为准**：`src/core/archive.ts` 里 `buildUpdatedSpec` 在提问**之前**执行（它的告警先于提问出现），`shouldUpdateSpecs` 只控制写入那一步。
